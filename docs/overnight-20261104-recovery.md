## Перед восстановлением

1. На хосте установить единственного владельца панели/очереди, источник запуска и PID. В этой песочнице видны только процессы сессии Codex, поэтому отсутствие PID здесь ничего не доказывает.

```bash
pgrep -f 'control_mvp[.]py|control_center[.]py|mailer_v2[.]py|lexradar_deals[.]py'
ss -ltnp 'sport = :8080'
lslocks -o PID,TYPE,MODE,PATH
```

Проверить worker.lock конкретного checkout, mailing.lock и прежний .mailer.lock. Последние два держатся только во время циклов: свободный lock не доказывает отсутствия потока между циклами. Дополнительно сверить PID, команду запуска локально и потоки своего процесса. Не печатать весь environment/секретные аргументы. Не запускать диагностический второй экземпляр панели. Watcher сделок и планировщик — разные роли; установить роль каждого PID.

2. Проверить активные jobs без конструктора Jobs:

```bash
python3 - <<'PY'
from pathlib import Path
import sqlite3
p = Path('.control-center-state/jobs.sqlite3').resolve()
with sqlite3.connect(p.as_uri() + '?mode=ro', uri=True) as db:
    print(db.execute("SELECT status,count(*) FROM jobs WHERE status IN ('pending','queued','running') GROUP BY status").fetchall())
PY
```

Непустой результат — не останавливать и не повторять задания. Недоступная БД — не считать jobs отсутствующими. Повторить проверку непосредственно перед согласованным остановом, исключив новые действия оператора. Jobs.close отменяет очередь/дочерний процесс, а __init__ меняет статусы, publish пересохраняет review и cleanup может удалить старые материалы. Пустая очередь сама по себе не гарантирует безопасного старта.

Получить отдельное окно обслуживания и актуальный согласованный backup кода с незакоммиченными изменениями, jobs и материалов, followup.sqlite3, CRM journals, всех mailing-файлов и приватной конфигурации. ## Код, данные и очередь восстанавливаются отдельно

**Код.** Bundle восстанавливать только в новый изолированный каталог, без запуска hooks/приложения. Пример для аварийного rehearsal, здесь не исполнялся:

```bash
umask 077
RECOVERY_DIR=$(mktemp -d /tmp/lexradar-recovery.XXXXXX)
git clone --no-checkout /home/golkonst/lexradar-backups/2026-11-03/web-control-5782753.bundle "$RECOVERY_DIR/code"
git -C "$RECOVERY_DIR/code" switch --detach 5782753177a2968217c19a18ba8d1ffb84924522
```

Bundle восстанавливает только зафиксированную историю. Нужные незакоммиченные правки брать из проверенного tar/нового снимка, сравнивать отдельно; не накладывать архив на работающий checkout. Текущие правки и новый followup новее исторического bundle. Проверить diff, синтаксис и пути ENGINE/PYTHON/Parser; не запускать main. Даже отдельный checkout использует общие внешние journals и mailer по абсолютным путям.

**Данные.** Архив извлекать только в отдельный приватный пустой каталог после проверки путей и ссылок. Изучить корневые префиксы, не использовать автоматический strip-components. Сверить пары PDF/HTML, hashes, review, результаты, SQLite quick_check в изолированной копии, отсутствие symlink; не обновлять пути и не исправлять исходные документы ради успеха. Восстанавливать согласованный набор одного момента, не смешивать случайно старый journal и новые PDF. Этот rehearsal здесь не выполнялся.

**Очередь и CRM.** Не подменять mailing.json, permissions/selection/archive, jobs.sqlite3 или CRM journals поверх живого состояния. Нужны сохранённые ID/intent, прежние lock-пути и новая read-only сверка полного Email (Sent/dateSent/sendAt), Account, Document и SHA-256. Старый локальный Draft/QUEUED не отменяет более новый Sent в CRM. Неизвестный POST/PUT остаётся HOLD; не очищать intent и не создавать новое письмо. Конфликт версий/неполный backup — остановить восстановление очереди, сохранить все варианты приватно и провести ручную сверку.

EspoCRM самостоятельно исполняет уже назначенные sendAt даже при остановленной панели. Останов панели не является отменой расписания. Не менять sendAt, разрешения или конфигурацию для «тестового запуска». Восстановление прав/секретов/расписания — отдельная разрешённая операция.
