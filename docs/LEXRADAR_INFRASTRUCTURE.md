## 1. Кратко: что построено и как войти

**Публичный адрес:** https://lr.prostoburo.com  **[ПРОВЕРЕНО 06.11]**

Доступ из любого браузера с интернетом: открыть адрес, пройти запрос логина/пароля HTTP Basic Auth, затем пользоваться интерфейсом Control Center. SSH, VPN и подключение к офисной сети для обычного просмотра панели не требуются. Пароль хранится отдельно от этого документа.

**Главный принцип:** LexRadar работает на внутренней виртуальной машине в офисной инфраструктуре. Офису не требуется собственный публичный IP и не нужно открывать входящий порт 8080 в интернет. Клиент FRP на LexRadar **сам устанавливает исходящее соединение** с публичным VPS. На VPS Nginx принимает HTTPS-запросы, проверяет пароль и передаёт их по туннелю в локальную панель.

### 1.1 Схема доступа из интернета

```text
Компьютер / телефон пользователя
          |
          | https://lr.prostoburo.com:443
          v
DNS REG.RU: lr.prostoburo.com -> 144.31.253.4
          |
          v
Публичный VPS 144.31.253.4 (Ubuntu 24.04)
  Nginx: HTTPS/TLS, сертификат Let's Encrypt,
         HTTP Basic Auth, перенаправление HTTP -> HTTPS
          |
          | reverse proxy: http://127.0.0.1:8091
          v
  frps (Docker, host network; порт управления туннелем 7000)
          ^
          | FRP: исходящее соединение frpc -> VPS:7000
          | TCP-прокси lexradar-control, remotePort=8091
          |
Внутренняя VM lexradar (Debian; Proxmox)
  frpc (Docker, host network, restart unless-stopped)
          |
          | localIP=127.0.0.1, localPort=8080
          v
  Python Control Center / control_mvp.py
  слушает 127.0.0.1:8080
          |
          +--> результаты Parser v3 и LexRadar-аудита
          +--> локальные журналы и файлы КП
          +--> подготовка данных и черновиков EspoCRM
```

**Важно о шифровании:** HTTPS защищает участок «браузер → Nginx на VPS». Внутри VPS Nginx обращается к FRP-прокси по HTTP на loopback. FRP использует собственное транспортное соединение VPS ↔ офис; наличие TLS именно на FRP-транспорте в текущей конфигурации **не подтверждено**. Нельзя утверждать, что все внутренние участки сквозным образом шифруются HTTPS.

### 1.2 Независимые направления

```text
Parser v3 -> список организаций/сайтов -> LexRadar audit
         -> КП HTML/PDF -> Control Center -> EspoCRM -> почта

Браузер -> HTTPS VPS -> FRP -> Control Center
```

Веб-панель — интерфейс управления и просмотра, а не отдельная копия движка аудита. Данные и процессы LexRadar остаются на внутреннем сервере. **Публичный адрес CRM — отдельный:** https://crm.prostoburo.com. Настройка `lr.prostoburo.com` не заменяет и не перенастраивает CRM.

## 3. Как работает внешний доступ: по шагам

1. Пользователь вводит `https://lr.prostoburo.com`.
2. DNS возвращает публичный адрес `144.31.253.4`.
3. Браузер устанавливает TLS-соединение с Nginx на VPS, порт `443`.
4. Nginx предъявляет сертификат Let's Encrypt для `lr.prostoburo.com`.
5. Nginx требует HTTP Basic Auth. Без верных учётных данных запрос не проходит дальше. Проверка без пароля дала **HTTP 401**.
6. После успешной авторизации Nginx передаёт HTTP-запрос на `http://127.0.0.1:8091` на том же VPS. Сохраняются заголовки `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`.
7. `frps` перенаправляет запрос по соединению с `frpc` на внутренней VM.
8. `frpc` обращается к `127.0.0.1:8080` внутри VM, где работает `control_mvp.py`.
9. Ответ панели возвращается тем же маршрутом обратно в браузер.

**Почему офисный роутер не требует проброса портов:** инициатор связи с VPS — внутренний `frpc`; соединение исходящее. Наличие публичного IP на VM LexRadar не требуется.

**Почему нельзя открывать `http://144.31.253.4:8091`:** этот порт служебный, предназначен для локального Nginx. Для него настроено правило firewall, отклоняющее внешние подключения. Внешний тест `Test-NetConnection ... -Port 8091` дал `TcpTestSucceeded: False` **[ПРОВЕРЕНО 06.11]**.

## 4. Конфигурация на внутренней VM: Control Center

### 4.1 Файлы

- `control_mvp.py` — текущая точка входа веб-панели.
- `control_pages.py` — обработчики страниц и проверки Host/Origin, изменённые для публичного домена.
- `/etc/systemd/system/lexradar-web.service` — systemd unit панели.

### 4.2 Фактический unit после настройки 06.11

```ini
[Unit]
Description=LexRadar Control Center Web UI
After=network.target

[Service]
Type=simple
User=golkonst
WorkingDirectory=/home/golkonst/src/LexRadar-web-control
ExecStart=/usr/bin/python3 /home/golkonst/src/LexRadar-web-control/control_mvp.py --parser-dir /home/golkonst/lexradar-data --results-dir /home/golkonst/src/LexRadar-compact --port 8080
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Ранее `ExecStart` указывал на устаревший `control_center.py`. **06.11 строка заменена на `control_mvp.py`**, выполнено `systemctl daemon-reload`, старый ручной процесс остановлен и сервис запущен. `systemctl is-active` вернул `active`; пользователь после этого открыл публичную панель.

**Автозапуск:** `systemctl is-enabled lexradar-web.service` → `enabled`. При обычной перезагрузке systemd запустит панель. `Restart=on-failure` позволяет перезапуск при аварийном завершении, но не гарантирует восстановление при любой внешней неисправности.

### 4.3 Основные команды на VM

```bash
# Статус
systemctl status lexradar-web.service --no-pager

# Запущена ли служба
systemctl is-active lexradar-web.service

# Включён ли автозапуск
systemctl is-enabled lexradar-web.service

# Логи последних событий
journalctl -u lexradar-web.service -n 100 --no-pager

# Перезапуск после изменения кода
su -
systemctl restart lexradar-web.service

# Проверка локального порта
ss -ltnp | grep ':8080'

# Проверка ответа без публикации в интернет
curl -I http://127.0.0.1:8080/
```

Если `curl -I` выдаёт 405/501, это не обязательно означает отказ сервиса: Python-обработчик может не поддерживать HEAD. Для проверки GET:

```bash
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' -H 'Host: localhost:8080' http://127.0.0.1:8080/
```

**Не запускать одновременно** `python3 control_mvp.py ...` в tmux и `lexradar-web.service`: оба претендуют на порт 8080. После 06.11 штатный способ — systemd, а не tmux.

### 4.4 Проверки Host и Origin

В `control_pages.py` сохранена локальная политика запросов и добавлена поддержка публичного домена:

- `Host: lr.prostoburo.com` принимается; дублирующиеся заголовки Host отвергаются.
- Для POST с публичным Host требуется **ровно один** заголовок `Origin: https://lr.prostoburo.com`.
- POST с `Origin: https://wrong.example` отклонён с **HTTP 403** **[ПРОВЕРЕНО 06.11]**.
- Локальные запросы `localhost:8080` продолжают обрабатываться по прежней политике.
- Дополнительные существующие проверки CSRF/подтверждения не отменялись.

**Ограничение проверки:** отрицательный тест чужого Origin успешен; реальное разрешённое изменяющее POST-действие из браузера после перехода на HTTPS **ещё не проверялось**. Для окончательной приёмки провести одно осмысленное штатное действие, заранее понимая, какие данные оно меняет. Не использовать реальные рассылки или массовые операции только ради теста.

## 6. Конфигурация публичного VPS

### 6.1 Nginx

- Основной файл сайта: `/etc/nginx/sites-available/lr.prostoburo.com`.
- Включение: символическая ссылка в `/etc/nginx/sites-enabled/`.
- HTTP Basic Auth: `/etc/nginx/.lexradar_htpasswd`.
- Сайт: `lr.prostoburo.com`.
- Локальный upstream: `http://127.0.0.1:8091`.
- Таймаут чтения прокси: `120s` в первоначальном конфиге.
- Certbot впоследствии дополнил конфигурацию TLS и HTTP→HTTPS redirect.

**Базовый фрагмент логики Nginx (не полная актуальная конфигурация после Certbot):**

```nginx
server_name lr.prostoburo.com;
auth_basic "LexRadar Control Center";
auth_basic_user_file /etc/nginx/.lexradar_htpasswd;
location / {
    proxy_pass http://127.0.0.1:8091;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 120s;
}
```

Не вставлять этот фрагмент вместо полного файла: после Certbot там присутствуют SSL-директивы и редирект.

### 6.2 Сертификат

- Выдан Certbot для `lr.prostoburo.com`.
- Успешная команда настройки: `certbot --nginx -d lr.prostoburo.com --redirect`.
- Срок действия при выдаче: **до 4 февраля 2027 года**.
- Certbot сообщил о настройке автоматического продления. Реальное успешное продление в будущем пока не наблюдалось.

Проверки:


### 6.3 Защита служебного порта 8091

Внешний доступ к `8091` запрещён правилом iptables:

```bash
iptables -I INPUT 1 ! -i lo -p tcp --dport 8091 -j REJECT
```

Для восстановления правила после перезагрузки создан и включён `/etc/systemd/system/lexradar-port-guard.service`:

```ini
[Unit]
Description=Block external access to LexRadar FRP port 8091
Before=docker.service
After=network.target

[Service]
Type=oneshot
ExecStart=/bin/sh -c '/usr/sbin/iptables -C INPUT ! -i lo -p tcp --dport 8091 -j REJECT 2>/dev/null || /usr/sbin/iptables -I INPUT 1 ! -i lo -p tcp --dport 8091 -j REJECT'
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

**[ПРОВЕРЕНО 06.11]:** сервис включён и активен, внешний тест TCP 8091 не прошёл. При этом `ufw` на VPS был `inactive`; защита порта реализована отдельным правилом iptables. При изменении firewall или Docker-сетей повторно проверить правило. Оно относится к IPv4; отдельная IPv6-публикация и IPv6-фильтрация не проверялись.

### 8.2 Движок LexRadar

Код: `/home/golkonst/src/LexRadar-compact`. Схема анализа **[РАНЕЕ]**:

```text

    -> dossier (материалы и доказательства)
    -> auditors / анализ
    -> сопоставление выводов и проверка доказательств
    -> READY / HOLD / REJECT / ERROR и иные статусы
    -> КП HTML/PDF при достаточных основаниях
    -> подготовка к CRM
```

Проверяются в том числе политика персональных данных, согласия, оператор, аналитика и cookies, сторонние виджеты, сведения о медицинских лицензиях, прайс и обязательные раскрытия. Недостаток доказательств должен вести к HOLD, а не к необоснованному утверждению о нарушении. Фактические правила аудита и статусы могут изменяться с развитием кода.

**Важно:** наличие результата аудита не всегда означает, что готовый PDF действительно существует. Перед передачей в CRM проверяется наличие и пригодность конкретного КП.

## 9. Что происходит после перезагрузки

### 9.1 Перезагрузка VM LexRadar

Ожидаемая последовательность:

1. Загружается Debian и системные службы.
2. Docker запускает `lexradar-frpc` по политике `unless-stopped`, если контейнер не был намеренно остановлен до перезагрузки.
3. `lexradar-web.service` запускает `control_mvp.py` от `golkonst`.
4. `frpc` соединяется с `frps` на VPS и регистрирует прокси `lexradar-control`.
5. Публичный Nginx снова получает ответы с локального `8091`.

**Не проводился реальный reboot-тест** после настройки 06.11. Проверены настройки автозапуска и работа после переключения на systemd, но полная цепочка восстановления после холодного старта ещё не испытана.

### 9.2 Перезагрузка VPS

Ожидается запуск Docker/frps, Nginx и oneshot-защиты порта `8091`; Certbot продолжит обслуживать сертификат. **Полный reboot-тест VPS не проводился**. Не перезагружать VPS ради проверки без отдельного окна обслуживания: там работает также CRM и другие сервисы.

## 10. Диагностика: панель не открывается

Двигаться **снаружи внутрь**, без массовых перезапусков.

### Случай A. DNS не находит `lr.prostoburo.com`

```bash
dig @1.1.1.1 lr.prostoburo.com A +short
```

Ожидается `144.31.253.4`. Если иное — проверить A-запись у REG.RU и время распространения DNS.

### Случай B. Сайт не открывается по HTTPS

На VPS проверить `systemctl status nginx`, `nginx -t`, `certbot certificates`, прослушивание `443`, доступность VPS. Не менять конфиг CRM.

### Случай C. Браузер просит пароль

Это штатная HTTP Basic Auth. Без пароля ответ **401** ожидаем. Если пароль утрачен — менять его через администратора VPS, не отключая защиту. Файл: `/etc/nginx/.lexradar_htpasswd`.

### Случай D. После пароля 502 Bad Gateway

Вероятна неисправность цепочки Nginx → `8091` → frps → frpc → `8080`.

1. VPS: `curl` на `127.0.0.1:8091` с правильным Host.
2. VPS: проверить Docker-контейнер `frps` и логи.
3. VM: `docker ps`, `docker logs --tail 100 lexradar-frpc`.
4. VM: `systemctl status lexradar-web.service`.
5. VM: `ss -ltnp | grep ':8080'`.

Не открывать порт `8091` наружу для «быстрого решения».

### Случай E. 403 на POST

Для публичного домена сервер требует `Origin: https://lr.prostoburo.com`. Если действие выполняется из штатного браузера и отклоняется, проверить DevTools/Network, заголовки Host и Origin, а также логи панели. **Не отключать проверку Origin целиком.** Негативный тест с чужим Origin намеренно дал 403.

### Случай F. Панель открывается, но данные CRM/КП неполные

Проверять журналы и файлы конвейера Parser/LexRadar/CRM отдельно. HTTPS/FRP не отвечает за качество данных. Не менять Nginx или firewall из-за ошибок связки Account/Document/Email Draft.

### Случай G. После правки кода видны старые страницы

На VM:

```bash
systemctl restart lexradar-web.service
systemctl status lexradar-web.service --no-pager
```

Затем обновить браузер. Не запускать параллельный экземпляр в tmux.

## 11. Безопасность и эксплуатационные ограничения

**Реализовано и проверено:**

- HTTPS на публичном домене.
- Basic Auth на Nginx.
- Закрытие прямого внешнего доступа к `8091` по IPv4.
- Привязка приложения к loopback `127.0.0.1:8080`.
- Отказ POST с неправильным Origin.
- Автозапуск панели через systemd и клиента FRP через Docker.

**Что не следует считать доказанным:**

- Успешный штатный POST через публичный браузер — ещё не протестирован.
- Реальное восстановление после перезагрузки обоих серверов — ещё не тестировалось.
- Полная внешняя оценка безопасности и аудит всех HTTP-маршрутов — не проводились.
- TLS на участке FRP-клиент ↔ FRP-сервер — не проверен.
- Ограничение частоты попыток Basic Auth, мониторинг, алерты, резервное копирование конфигураций и проверка восстановления — не подтверждены.
- IPv6-защита порта 8091 — не проверена.

**Правила:**

1. Никогда не коммитить `/root/frp/frpc.toml`, `.env`, токены API, файлы htpasswd и приватные ключи в публичный GitHub.
2. Не публиковать в переписке действующие пароли и токены; при случайном раскрытии — ротировать.
3. Перед редактированием Nginx делать копию файла и `nginx -t` до reload.
4. Не изменять CRM `8090`, её Nginx-сайт, Docker-контейнеры и почтовую интеграцию при обслуживании панели.
5. Не отключать firewall-правило `8091`.
6. Не держать одновременно ручной процесс `control_mvp.py` и systemd-сервис.
7. При изменении публичного домена синхронно менять DNS, Nginx, сертификат, правила Host/Origin приложения.
8. Перед изменениями фиксировать рабочее состояние и предусматривать откат.
