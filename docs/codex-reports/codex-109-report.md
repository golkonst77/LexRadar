# LexRadar №109 — КП только по подтверждённым недостаткам

21.10.2026. №108 полностью завершён как минимальный срез с зафиксированными ограничениями и опубликован **до начала №109**. [Код №108, b5516fdf507df028c9d4a3e8eb117256bb85166d](https://github.com/golkonst77/LexRadar/commit/b5516fdf507df028c9d4a3e8eb117256bb85166d), [отчёт №108](https://github.com/golkonst77/LexRadar/blob/feature/lexradar-108-free-first/docs/codex-reports/codex-108-report.md).

**Результат №109:** общий генератор выпускает короткий проект КП по подтверждённым существенным недостаткам. Текст показывает факт → последствие → документы и ТЗ для исправления. Точная цитата без подтверждённого дефекта больше не достаточна для выпуска КП.

[Обезличенное синтетическое КП №109](lexradar-109-demo.html). GitHub показывает HTML-код; скачайте файл и откройте в браузере для просмотра оформления. Пример содержит два настоящих для синтетической фикстуры дефекта, а не результаты реального клиента.

## Что изменилось в коммерческом тексте

- Одно короткое вступление: экспресс-аудит уже проведён, предлагаются документы и подробное задание вебмастеру для устранения подтверждённых недостатков. Убрано повторное вступление и продажа одной только дополнительной проверки.
- В блоке «На вашем сайте выявлены недостатки» остаются только подтверждённые существенные FAIL с проверенным источником и координатами. Каждый пункт: короткий заголовок, предложение факта, конкретное последствие, предлагаемая работа. В примере политика одновременно указывает 30 и 90 дней для одинаковых заявок; согласие прямо объявлено включённым в договор без отдельного оформления.
- Автоматический текст фактов строится из проверенного узкого правила, а не произвольного пояснения: подмена пояснения вымышленной утечкой не меняет клиентскую карточку.
- Дедупликация по типу недостатка предотвращает несколько одинаковых рисков. Максимум четыре разных существенных карточки, одна находка допустима. Обнаруженные наблюдения и остальные доказательства сохраняются во внутреннем пакете.
- REVIEW/PARTIAL/UNKNOWN, простое упоминание Метрики, отсутствие checkbox и общий текст о медицинских данных не становятся подтверждёнными дефектами. Клиент не видит технические коды, хеши, методологию или вопросы «необходимо проверить».
- Обязательный раздел политики ПДн сохранён вне списка недостатков и описывает конкретные результаты работы: согласованные сроки хранения, удаление/уничтожение, условия передачи. Он не объявляет неподтверждённый дефект политики. Исходные статусы POLICY-3, цитаты и источники сохраняются во внутреннем JSON. Подтверждённый независимым локальным заключением FAIL политики может стать отдельной конкретной карточкой.
- По умолчанию используются «организация», «клиенты», «посетители», «ваш сайт»; прежняя «жалоба пациента» заменена на «жалоба клиента». Отраслевые претензии по одному названию бизнеса не добавляются.

## Доказательства и пределы автоматизации

Два автоматических правила из №108 сохранены: явное противоречие сроков одной категории в политике и прямое заявление о включении согласия в договор без отдельного оформления. Для карточек повторно проверяются точные цитаты/координаты, полнота воспроизведённого источника и отсутствие явно обозначенного примера/цитаты. Другие формулировки остаются REVIEW.

Добавлены словари карточек аналитики, формы, рекламного согласия, сроков/удаления/передачи и медицинского согласия. Это **не новые автоматические детекторы**. Для дополнительных типов требуется независимое локальное подтверждение факта, применимости и недостатка с автором, датой и хешем проверенного пакета. Статическая ссылка на аналитический скрипт не удовлетворяет этому условию. События реального браузера, доставки рекламы и обработки здоровья автоматически не устанавливаются.

Медицинская карточка дополнительно требует явного отраслевого контекста medical и воспроизведённого указания «Медицинская организация» в источниках. Это узкий консервативный механизм, а не классификатор всех отраслей. Без отраслевого подтверждения специфический медицинский пункт исключается. Рекламный пункт включается только при отдельном подтверждённом дефекте рекламного сценария. Правовая квалификация не поручена шаблону.

Для случаев вне автоматических правил оператор должен отдельно подтвердить недостаток; модуль не доказывает правомерность такого человеческого заключения сам по себе. Отправка клиенту всё равно требует отдельного утверждения.

## Общий механизм и безопасный HOLD

Единый фильтр `commercial_cards.cards_for` и общий `client_proposal.render_client` используются бесплатным конвейером, операторским запуском, экспортом, пакетным путём и review bundle. Старый голый признак confirmed=True не обходит фильтр.

- Бесплатный путь: GO по подтверждённым дефектам без AI; иначе AI_PENDING_APPROVAL либо HOLD, как в №108.
- Оператор: воспроизводит бесплатные проверки на том же досье, сверяет хеш и допускает подтверждённый локальный FAIL POLICY-3. Историческая квалификация сохраняется отдельно как legacy_qualification.
- Экспорт: одной подтверждённой находки достаточно; прежнее требование минимум двух снято. При нуле недостатков сохраняются только внутренний отчёт и HOLD. Имя выходного файла стало универсальным `proposal.html`; это намеренное изменение прежнего клиентского имени файла.
- Пакетный путь: без подтверждённого недостатка квалификация становится HOLD, файл КП не создаётся; существующие разрешения AI не ослаблены.
- Review bundle: старые доказанные текстовые наблюдения сохраняются для оператора, но без подтверждённого дефекта не дают клиентский HTML. Для независимых карточек требуется полноценный Collector-пакет; старый минимальный комплект оригиналов не достаточен.

Шаблон не читается при раннем HOLD. При настоящем GO проверяется его неизменность. Ошибки целостности/источников не превращаются в коммерческие утверждения.

## Что осталось до запуска

1. Предоставить локальный утверждённый оригинал шаблона с указанным хешем; он не публикуется вместе с контактами и примером получателя.
2. Проверить применимость узких правил и дополнительные независимые заключения на согласованных реальных материалах. Нестандартные случаи автоматически не повышать до FAIL.
3. При необходимости реализовать отдельный безопасный динамический worker для аналитики/форм/рекламных сценариев; сейчас это REVIEW.
4. Согласовать выпуск оператором и отдельно утвердить отправку. Автоматическая рассылка отсутствует.
5. Провести обычную процедуру ревью и интеграции кода до production; в этой работе merge/deploy не выполнялись.

Публикация прошла проверку на известные клиентские идентификаторы, секреты, контакты и внутренние пути. Клиентских исходников, сырого HTML сайтов и ответов моделей в ней нет. Платных AI-запросов, отправки клиенту, merge, deploy, restart production и изменений main не было.
