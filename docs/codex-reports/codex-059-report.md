## Вывод и уверенность

Наиболее конкретная обоснованная причина двух ошибок — истечение 45-секундного ожидания внутри HTTP-транспорта. Уверенность высокая, но это вывод по времени и коду, а не сохранённое свидетельство типа исключения. Точная фаза (DNS/TCP/TLS/отправка/ожидание HTTP-заголовков либо чтение тела) и внешняя причина неизвестны: основной orchestrator теряет уже сформированную безопасную диагностику ProviderError. Этот дефект журналирования подтверждён исходниками и отдельным офлайн-воспроизведением, уверенность полная.

Доказательств поломки алгоритма чтения HTTP, ошибки модели, неверного ключа, отказа OpenRouter, ограничения тарифа или необходимости увеличить timeout нет. Локально восстановить утраченные сведения именно этих двух исключений невозможно. Сетевой таймаут не доказывает отсутствие обработки запроса или списания на стороне сервиса.

`request_sent` выставляется orchestrator перед вызовом provider.complete: это признак начатой попытки, а не доказательство доставки HTTP-запроса. Ошибка могла произойти до передачи запроса серверу. Обе длительности почти точно совпадают с timeout_seconds=45 текущего фиксированного профиля. Сам код transport_error шире timeout и допускает другие сетевые/HTTP-протокольные исключения; поэтому категорически установить TimeoutError только по сохранённому коду нельзя.

## Путь исполнения и timeout

- `src/lexradar/single_auditor.py`: профиль 45 s, один повтор; DeepSeekAdapter наследует OpenRouterProvider и добавляет проверки фиксированного профиля и токенных границ.
- `src/lexradar/auditors/provider.py`: OpenRouterProvider строит нестриминговый JSON-запрос (`stream=false`, max_tokens=4000, JSON response format), передаёт timeout и предел ответа в транспорт. Ответ модели и usage разбираются только после полного получения тела. Отказ парсинга дал бы другой код ошибки.
- OpenRouterTransport использует urllib build_opener(NoRedirects()), POST на фиксированный endpoint. Стандартный opener может использовать proxy-настройки окружения; их значения не читались. Наличие или неисправность proxy не установлены.
- Фаза open включает весь opener.open до получения HTTP-заголовков: подключение, возможный proxy/TLS, отправку и ожидание ответа. В open передаётся timeout=45. Отдельных фаз подключения и ожидания заголовков нет.
- Deadline вычисляется перед open. После заголовков фаза read получает остаток общего времени; перед каждым read1 socket timeout обновляется. Даже периодические байты тела не продлевают общий бюджет 45 s. Это важно для долгого нестримингового ответа, но наличие таких байтов в реальном запуске неизвестно.
- TimeoutError, URLError, OSError и HTTPException преобразуются в retryable transport_error с безопасными phase/kind/http_status/received_bytes. Для TimeoutError и URLError(TimeoutError) kind=timeout. Отдельный transport_timeout/kind=deadline возникает при проверке истёкшего бюджета между чтениями. Поэтому transport_error совместим с обычным socket timeout и не исключает таймаут.
- HTTPError возвращает HTTP-статус и пустое тело, затем provider формирует http_NNN; наблюдаемые transport_error не являются сохранённым HTTP 401/429/5xx. Обрыв тела формирует kind=incomplete_read, также с transport_error.
- Ограничение: socket timeout и проверки между read1 не гарантируют строгий wall-clock deadline при медленном framing или нескольких операциях внутри open/read1. Это не доказанная причина данного запуска.

## Потеря полезной диагностики

`ProviderError.diagnostics` уже содержит четыре безопасных поля. В `auditors/orchestrator.py`, except ProviderError, сохраняются лишь exc.code и retryable; diagnostics не передаются в RequestLog. В `auditors/models.py` у RequestLog нет соответствующего поля. В результате analysis.json и requests.jsonl одинаково теряют фазу, категорию ошибки, статус и объём ответа. Исходное исключение сохранено через exception chaining только в памяти; orchestrator его перехватывает, а traceback в артефактах отсутствует.

Для сравнения, отдельный `auditors/compact_pipeline.py` сохраняет provider_diagnostics. Первый Single DeepSeek A шёл через основной orchestrator, поэтому это поведение compact не помогает.

Транспорт намеренно не сохраняет произвольный текст исключений, HTTP error body и headers: там могут быть секреты. Раскрывать их для этой диагностики не нужно. Более подробные фиксированные категории DNS/TLS/connection и числовой errno могут быть полезны позже, но это дополнительная задача, а не необходимое минимальное исправление.

## Минимальное предлагаемое исправление

Изменить только models.py и orchestrator.py, без изменения архитектуры и самого HTTP-транспорта:

1. Добавить в RequestLog необязательное типизированное поле provider_diagnostics с ограниченным набором phase (open/read), kind (timeout/deadline/incomplete_read/http_protocol/network), http_status и received_bytes. Старые журналы без поля должны продолжать читаться.
2. На каждой попытке инициализировать диагностику заново и в except ProviderError переносить только эти четыре разрешённых поля в RequestLog. Не копировать произвольный словарь или str(exc)/str(exc.__cause__), payload, ключ, заголовки либо тело ответа.
3. Офлайн-регрессией проверить оба выходных формата, обе фазы timeout, отсутствие диагностики от предыдущей попытки после успешного повтора, совместимость старого JSON и отсутствие секретных строк.

Это устранит подтверждённую диагностическую ошибку; не обещает устранить внешнее ожидание. Повышение timeout либо изменение retries сейчас не обоснованы; увеличение одного поля профиля затрагивает проверки равенства profile() и не должно делаться обходом этих проверок. Исправление кода в задании не применялось: для диагностики достаточно воспроизведения и конкретного предложения, пользователь попросил минимизировать изменения.
