## Реализовано

### Изолированный worker

Новый `browser_evidence.py` запускает установленный Playwright/Chromium в отдельном POSIX-процессе. По умолчанию: 30 секунд работы плюс до 5 секунд на импорт/завершение; родитель принудительно завершает свою группу процессов при зависании. Браузер не скачивался, новые зависимости не устанавливались.

Браузер работает offline, с заблокированными service workers и WebSockets; прямой браузерный egress дополнительно направлен в недоступный локальный proxy. Ответы разрешённых HTTP-запросов передаются через route.fulfill из существующего DNS-pinned Fetcher. Никакого route.continue или browser request.fetch нет. Тела используются в памяти для рендеринга и нигде не сохраняются.

Живые запросы проходят прежние AddressPolicy, TLS-проверку, robots, задержки и лимиты Collector. Privacy-адаптер CrawlSession сохраняет проверку robots, но не записывает сырой journal и тела robots.txt. Ошибки robots запрещают запрос, 404/410 означают отсутствие правил, как в Collector. Redirect ограничен исходным origin и повторно проверяется до обращения к новой цели; cross-origin redirect блокируется. HTTP-прокси окружения не обходится: несовместимый с pinning транспорт отказывает закрыто.

Запрещены literal IP, внутренние имена, credential URLs, нестандартные порты и схемы. Окончательный DNS-ответ на каждый реальный запрос проверяется существующим AddressPolicy. Общий HTTP-бюджет: 24 попытки, не более 8 origins, 5 MB суммарно, 1 MB на ответ, до 5 секунд на I/O. Период наблюдения по умолчанию 600 ms после загрузки и после разрешённого действия. Это короткое ограниченное окно, а не обещание полноты.

Одна исходная страница на контекст. Вторичные навигации, iframe, все non-GET и неизвестные XHR/fetch блокируются. Worker не вводит данные и не отправляет формы; установлен защитный init-script для submit/requestSubmit и submit-event. Отдельный тест проверяет автоматические попытки отправки и блокировку POST.

Это процессная изоляция и сетевое посредничество, а не полноценный контейнер с cgroup/OS egress policy. Перед production для произвольного недоверенного JavaScript нужна отдельная проверка sandbox и ресурсов.

### Три состояния и факты

Для локальных фикстур выполняются before_choice, after_reject, after_accept в трёх чистых browser contexts. Клики разрешены только по заранее известным #lr-reject/#lr-accept, если это видимая единственная button type=button вне формы. Фикстура разрешена только на зарезервированном .invalid origin, все её сетевые ответы синтетические.

Для живого сайта выполняется **только before_choice**. Нет опции бесконтрольно кликать «Согласен» или «Отклонить» на реальном сайте.

Протокол различает библиотеку аналитики и measurement endpoint: Яндекс.Метрика watch и tag.js, Google Analytics collect и загрузчики GTM. Записываются этап, исходный origin, безопасный destination origin без пути/query/fragment, тип ресурса, метод, относительное время, классификация endpoint и исход транспорта. Попытка браузера, синтетическое fulfillment и реальный network_response — разные факты. network_sent=true означает HTTP-запрос транспортом, не доказательство получения персональных данных или правомерности обработки.

В протокол не входят cookies, заголовки, токены/query, path/counter ID, значения/имена полей и тела запросов/ответов. Не сохраняются HAR, screenshots реальных сайтов, storage_state или raw console/error logs. Cookie и Authorization не читаются и не пересылаются; Set-Cookie не воспроизводится. Это защищает данные, но может менять поведение сайта и ограничивает доказательную силу отсутствия событий.

### WEB-03: ограниченное наблюдение

Сохранены только структурные признаки реально видимых форм: локальные индексы, тип поля, checked, required, наличие label, признаков текста согласия/ПДн/рекламы и ссылок. Видимый cookie UI и управляющие кнопки фиксируются по DOM, а не по одному HTML-упоминанию. Внешний iframe отмечается как недоступный, без проникновения в его DOM.

Полные тексты согласий, содержимое ссылок и значения полей намеренно не сохраняются. Поэтому WEB-03 выполнен частично как безопасная структурная инвентаризация, а не полная проверка согласия. Само отсутствие checkbox или предварительная отметка не дают FAIL.

WEB-02 получает относительную ссылку и SHA-256 протокола, техническое предупреждение и REVIEW. WEB-03 получает минимальные DOM-признаки. Сырые события не попадают в клиентский HTML.

Даже measurement request до выбора **не создаёт юридический FAIL или commercial GO**: необходимо отдельно подтвердить фактические данные, применимое основание и конкретный недостаток. Автоматическая такая квалификация не реализована. Без другого подтверждённого существенного недостатка результат остаётся AI_PENDING_APPROVAL/HOLD, обвинительное КП отсутствует. Сохраняются ручное утверждение, client_release_allowed=false, automatic_send_allowed=false, sent=false. Новых AI-вызовов и расходов нет.

## Воспроизведение локально

Из изолированного checkout, с уже установленными зависимостями и Chromium:

```bash
PYTHONPATH=src:. python -m lexradar.browser_evidence https://business.example.invalid/ \
  --fixture tests/fixtures/browser110/consent.html --output /path/to/new-protocol.json

PYTHONPATH=src:. python -m lexradar.browser_evidence https://business.example.invalid/ \
  --fixture tests/fixtures/browser110/before-choice.html --output /path/to/another-protocol.json

PYTHONPATH=src:. python -m pytest -q tests/test_browser_evidence_110.py \
  tests/test_free_first_108.py tests/test_commercial_proposal_109.py

PYTHONPATH=src:. python -m lexradar free-first --dossier /path/to/local/dossier \
  --browser-check --output /path/to/new-private-result
```

Последняя команда — opt-in живое наблюдение URL существующего досье. Для полностью синтетической интеграции добавьте --browser-fixture tests/fixtures/browser110/before-choice.html и используйте синтетическое досье с .invalid URL. Выходные пути должны быть новыми. Без установленного браузера/при таймауте получается REVIEW, установка браузера автоматически не запускается.
