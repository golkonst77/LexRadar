## Причина и предел доказательности

Код transport_error создаётся исключительно обработчиком URLError,
TimeoutError, OSError либо http.client.HTTPException в OpenRouterTransport.post.
Следовательно, pipeline не дошёл до успешного разбора envelope и compact JSON.
Ошибка схемы/цитат, несовпадение модели и отсутствие usage имели бы другие коды.
Это сбой передачи/чтения HTTP-ответа, а не свидетельство неудачной генерации.

Точный низкоуровневый диагноз исторической попытки **не восстановим из
имеющихся артефактов**: сохранён только общий код; нет типа исходного исключения,
этапа, HTTP-статуса, числа прочитанных байтов, generation ID или traceback.
Нельзя доказанно назвать причиной timeout, разрыв TLS, IncompleteRead либо
ошибку работы с сокетом. Время генерации 2.57 с не измеряет полное время
клиентского запроса. Старое сообщение о DNS из задания №39 не объясняет
подтверждённую платную генерацию этой попытки.

В коде обнаружено хрупкое управление чтением: цикл обращался к приватной
цепочке response.fp.raw._sock перед каждым read1, а завершение определял
только пустым чтением. Теперь учитываются закрытие HTTPResponse и нулевая
оставшаяся Content-Length, сокет захватывается до чтения. Это укрепление
обработки завершения ответа; считать его доказанной причиной №39 нельзя.
Отдельный воспроизводимый дефект: read1 не гарантирует IncompleteRead при
преждевременном EOF ответа с Content-Length. Старый transport принимал
обрезанное тело как HTTPReply, после чего причина могла теряться за ошибкой
JSON envelope. Теперь такой случай явно классифицируется как incomplete_read.

## Исправления

- Чтение заканчивается по состоянию HTTPResponse/Content-Length; сохранены
  общий deadline, ограничение размера и запрет redirects. Chunked и ответы
  без Content-Length продолжают читаться до штатного завершения framing.
- ProviderError несёт безопасную диагностику: phase, kind, http_status,
  received_bytes. Исключения транспорта различаются по фиксированным
  категориям timeout/incomplete_read/http_protocol/network; deadline отдельно.
  Тексты исключений, тела, заголовки и ключи не попадают в отчёт.
- compact pipeline сохраняет эту диагностику в compact-analysis.json.
- Скрипт №39 при неуспехе явно предупреждает о возможном списании и требует
  сохранить ledger/маркер и сверить Logs. Проверки O_EXCL, flock, ledger,
  маршрута и запрета повторной попытки сохранены. Скрипт не запускался.
- Новые тесты используют настоящий HTTPResponse с байтовым потоком в памяти:
  Content-Length, chunked с пробельным префиксом, close-delimited, размер,
  усечённые Content-Length/chunked и безопасная диагностика. Проверено
  сохранение диагностики pipeline и блокирование второй попытки.

## Восстановление без генерации

Официальный [GET /generation](https://openrouter.ai/docs/api/api-reference/generations/get-request-&-usage-metadata-for-a-generation)
возвращает metadata, модель, провайдера, токены и стоимость по generation ID;
сам по себе он не возвращает текст completion.
Официальный [GET /generation/content](https://openrouter.ai/docs/api/api-reference/generations/get-stored-prompt-completion-and-error-content-for-a-generation)
предусматривает сохранённые input и output.completion по ID. Документация
содержит также ответ 403 «Only management keys can perform this operation».
Наличие успешной записи Logs ещё не гарантирует сохранение/доступность текста.

Для этой попытки нужно взять generation ID из записи Logs и проверить
сохранённый output в интерфейсе либо выполнить только GET metadata/content
с подходящими правами. Если контент доступен, сохранить его приватно отдельно
от исходных артефактов, сверить input с отправленным пакетом и prompt,
модель/маршрут/finish_reason/usage с metadata, затем локально проверить JSON,
схему compact и цитаты штатным validate_compact. Не подменять отсутствующие
поля предположениями. Ledger при этом в рамках задания остаётся неизменным.

В локальных результатах ID и completion отсутствуют. Поэтому получить
конкретный ответ здесь пока нельзя; авторизованные GET не выполнялись.
Если сервис не сохранил текст, одни токены и стоимость не позволяют
восстановить содержание. Повтор POST, в том числе с надеждой на кэш,
не является безопасным восстановлением и не разрешён.
