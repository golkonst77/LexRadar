# LexRadar Control Center — справочник пользователя и администратора

**Версия:** 30.10.2026 · **Репозиторий:** `golkonst77/LexRadar` · **Ветка:** `web-control-development`

> Это справочник именно панели Control Center, а не всей системы LexRadar. Основной сценарий и ограничения определяет [LEXRADAR_PRODUCT_PLAN.md](../LEXRADAR_PRODUCT_PLAN.md). При расхождениях фактическое поведение проверять по коду и рабочему состоянию. Отправка писем автоматически **не выполняется**.

## 1. Назначение и схема

Control Center — небольшой локальный Python HTTP-сервер с веб-страницами и кнопками, который объединяет уже существующие инструменты:

```text
Браузер → Control Center (Python, порт 8080)
             ├─ 1. Parser v3: сбор организаций и контактов
             ├─ 2. LexRadar: анализ сайтов, квалификация, КП
             ├─ 3. READY: просмотр актуальных HTML/PDF
             └─ 4. EspoCRM: Account → Document → Email Draft
                                      (без отправки)
```

Панель не заменяет Parser v3, движок LexRadar или EspoCRM. Это единый операторский интерфейс для последовательного запуска и проверки результатов.

## 3. Как открыть панель

Панель рассчитана на локальный доступ к серверу через SSH-туннель. В браузере на компьютере оператора: **http://127.0.0.1:8080** — только при активном туннеле на порт 8080 сервера.

Пример туннеля с компьютера оператора (заменить адрес сервера на реально используемый):

```bash
ssh -L 8080:127.0.0.1:8080 golkonst@<адрес-сервера>
```

На самом сервере запуск из каталога проекта:

```bash
cd /home/golkonst/src/LexRadar-web-control
python3 control_mvp.py \
  --parser-dir /home/golkonst/lexradar-data \
  --results-dir /home/golkonst/src/LexRadar-compact \
  --port 8080
```

В используемой конфигурации возможен фоновый запуск:

```bash
cd /home/golkonst/src/LexRadar-web-control
nohup python3 control_mvp.py \
  --parser-dir /home/golkonst/lexradar-data \
  --results-dir /home/golkonst/src/LexRadar-compact \
  --port 8080 > /home/golkonst/control-center.log 2>&1 < /dev/null &
```

Проверить процесс: `pgrep -af 'python3 control_mvp.py'`. Посмотреть последние сообщения: `tail -n 80 /home/golkonst/control-center.log`. **Не запускать вторую копию на том же порту.** На 30.10.2026 запуск через `nohup` не гарантирует автоматический старт после перезагрузки; systemd-служба пока не подтверждена.

## 4. Краткая инструкция оператору — четыре шага

### Шаг 1. «Собрать организации»

Открыть **«Сбор организаций»** (`/collect`), выбрать отрасль и требуемое количество пригодных организаций N, проверить параметры и запустить Parser v3. Дождаться окончания; экран показывает ход сбора, просмотренные карточки и количество пригодных организаций. N означает целевое число пригодных записей, а не число просмотренных карточек.

После завершения перейти по кнопке **«Перейти к проверке сайтов»**: она сохраняет контекст текущего запуска.

### Шаг 2. «Проверить сайты»

Открыть **«Проверка сайтов»** (`/analysis`). Проверить список и запустить анализ новых сайтов: всех доступных или выбранной части. Дождаться завершения. Результаты различаются:

- **READY** — есть актуальное коммерческое предложение для дальнейшей работы.
- **REJECT** — коммерческое предложение не подготовлено по результатам квалификации.
- **HOLD** — требуется дополнительная проверка/разрешение вопроса.
- **ERROR** — техническая ошибка; это не коммерческий отказ.

Для ошибок предусмотрен отдельный экран **«Ошибки анализа»** и действие **«Повторить ошибки»** с предпросмотром: не нужно заново собирать организации или повторять успешно обработанные сайты. Работу этой кнопки на реальной партии ещё следует отдельно проверить.

### Шаг 3. «Готовые предложения»

Открыть **«Готовые предложения»** (`/proposals`). Просмотреть список READY, открыть HTML/PDF и убедиться, что название организации, сайт, содержание и контактные данные соответствуют нужному клиенту.

Для нормализованного домена отображается одно **актуальное** READY-КП. Если последующий анализ завершился HOLD/REJECT/ERROR, прежнее подтверждённое READY не уничтожается, но статус последнего анализа показывается отдельно. **Обновление КП в локальном Control Center само по себе не заменяет ранее загруженный PDF в CRM.**

### Шаг 4. «Передать в CRM»

Открыть **«Передача в CRM»** (`/crm`), выбрать проверенное READY-КП и просмотреть предварительные данные. Выполнить предусмотренное интерфейсом подтверждение поиска/создания **Account**. После `ACCOUNT_VERIFIED` подготовить **Document** с PDF и **Email Draft**.

Итог **`DRAFT_VERIFIED`** означает, что проверенный черновик создан и его можно открыть прямой ссылкой в EspoCRM. Проверить получателя, связанный Account, тему, текст, статус «Черновик» и PDF-вложение. **Нажатие «Отправить» в EspoCRM — отдельное ручное действие; Control Center автоматически письма не рассылает.**

При `HOLD`/`HOLD_IDENTITY`, неопределённой ошибке или конфликте идентичности **остановиться** и разобраться; не сбрасывать журналы, не повторять POST вслепую и не обходить блокировку выбором другого юридического лица. При отсутствии email возможен `DOCUMENT_VERIFIED_NO_DRAFT` без создания письма.

Подробная техническая процедура: [crm-controlled-run.md](crm-controlled-run.md), [espo-integration.md](espo-integration.md), [espocrm_lexradar_reference.md](espocrm_lexradar_reference.md). В них есть исторические сведения о старых CRM-записях: перед применением сверять с актуальным состоянием.

## 6. Что сохранять и как восстанавливать

**Код:** GitHub, ветка `web-control-development`. **Рабочие данные:** каталоги Parser v3, результатов LexRadar, `.control-center-state`, журналы в `~/.local/state/lexradar` и конфигурация CRM — отдельный защищённый бэкап с сохранением прав доступа. Данные EspoCRM хранятся в самой CRM и требуют её собственной процедуры резервного копирования.

При восстановлении сначала вернуть код и зависимости, затем отдельно восстановить данные/настройки из проверенного бэкапа, убедиться в доступности EspoCRM и лишь после этого запускать `control_mvp.py`. **Нельзя** просто удалить журналы CRM для «чистого старта»: это может привести к дубликатам или потере связей с уже созданными Account/Document/Email.

Обновление кода с GitHub на сервере после изменения ветки:

```bash
cd /home/golkonst/src/LexRadar-web-control
git status --short
git pull --ff-only origin web-control-development
```

Выполнять `git pull` только после проверки незакоммиченных локальных изменений; при конфликте остановиться и разобраться. После обновления работающий Python-процесс **не подхватывает автоматически** все изменения исходников: нужен контролируемый перезапуск.

## 7. Правила безопасной эксплуатации

1. Не включать автоматическую рассылку писем.
2. Перед CRM проверять юридическое лицо, сайт, адрес получателя и PDF.
3. Не удалять рабочие журналы и не создавать дубликаты Account/Document/Email ради обхода HOLD.
4. Не хранить API-ключи, реальные базы, рабочие PDF и журналы на публичном GitHub.
5. При изменениях интерфейса сверяться с `LEXRADAR_PRODUCT_PLAN.md`; сохранять понятный порядок четырёх шагов.
6. После значимых рабочих изменений обновлять этот справочник и фиксировать изменения в Git.

## 8. Быстрые ответы

**Где кнопки?** В локальной веб-панели на порту 8080 через SSH-туннель.

**Почему READY меньше, чем найдено организаций?** Не все сайты проходят коммерческую квалификацию; отдельно возможны HOLD и технические ERROR.

**Почему старое READY видно после новой ошибки?** Последнее подтверждённое КП сохраняется; последний статус анализа показывается отдельно.

**Где письмо?** В EspoCRM по ссылке из результата `DRAFT_VERIFIED`; оно остаётся черновиком.

**Можно ли восстановить всё только из GitHub?** Нет. GitHub содержит код и инструкции, но не полную рабочую базу и не данные EspoCRM.

**Что делать, если панель не открывается?** Проверить SSH-туннель, процесс `control_mvp.py`, порт 8080 и `control-center.log`.

  КП открывается из списка предложений по прежнему адресу `/crm/preview`.
- **Служебное** (`/service`) — задания, диагностика, отчёты и контакты.

Общие стили встроены в серверный шаблон `control_center.py` и применяются
также к страницам `control_pages.py`. Старый запуск `control_center.py`
сохраняет свои маршруты: предложения доступны через `/reports`, служебные
настройки через `/settings`; четырёхшаговый обзор предоставляет MVP.

Светлый фон #F7F8FA, белые карточки, синий акцент #2563EB, шрифт
Inter (если установлен) либо system-ui, базовый размер 16 px.
Внешних шрифтов, CDN, JavaScript и новых зависимостей нет.
На широком экране четыре карточки в ряд, на планшете две, на телефоне одна.
Основные действия синие, вторичные спокойные, остановка выделена отдельно.
Статусы сохраняют текст READY/REJECT/HOLD и сообщения об ошибках:

Прогресс показывает реальные счётчики, длительность и текущий сайт,
если эти данные доступны. Штатное обновление каждые 5 секунд сохранено;
выдуманных процентов нет. POST/GET, подтверждения, CSRF/Origin/Host,
выбор лидов и ссылки на PDF/HTML сохранены. Редизайн не меняет CRM-схему,

## Сохранение в Git

В среде выполнения `.git` доступен только для чтения: `git fetch origin`
завершился ошибкой записи `.git/FETCH_HEAD`. Актуальность remote проверить

других задач сохранены. Для ручной публикации из рабочей папки с правом
записи в Git, после просмотра diff и staged-файлов:

```bash
git diff -- control_center.py control_mvp.py control_pages.py docs/CONTROL_CENTER_GUIDE.md
git diff --cached --name-only
git add -- control_center.py control_mvp.py control_pages.py docs/CONTROL_CENTER_GUIDE.md
git commit --only -m "Refresh Control Center with accessible light SaaS interface" -- control_center.py control_mvp.py control_pages.py docs/CONTROL_CENTER_GUIDE.md
git push origin web-control-development
```

Если remote продвинулся, push будет отклонён: сначала нужно безопасно
согласовать изменения, сохранив чужие правки. Force push не применять.
