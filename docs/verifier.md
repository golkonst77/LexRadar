# Independent Legal Verifier v0.4

Верификатор исследует досье самостоятельно, затем сопоставляет результат с A/B.
Он не вызывает Gateway и не отправляет сообщения. `VerificationReport` — внутренний
результат для независимой проверки и утверждения человеком, а не решение GO.

## Архитектура и независимость

- `packets.py`: проверка досье v0.2 и реестра, построение точных пакетов.
  `prepare_independent` не принимает отчёты A/B. В первом пакете нет их выводов,
  журналов, ответов или истории. Содержимое сайта остаётся недоверенными данными.
- `pdf_inventory.py` / `materials.py`: ограниченная инвентаризация текстовых страниц
  PDF в дочернем процессе (512 MiB, 5 секунд CPU, общий таймаут Collector).
  Повторная проверка артефактов завершает подготовку пакета.
- `registry.py`: локальные нормативные записи, хеши, редакции, сроки перепроверки.
- `rules.py`: проверка цитат и статусов, применимости, ошибочных технических выводов,
  дубликатов и подтверждений человека. Самоуверенность LLM не подтверждает норму.
- `runtime.py`: отдельные версионированные промпты `independent-v1` и `comparison-v1`,
  существующий транспорт OpenRouter v0.3, ограниченные повторы и общий бюджет.
- `orchestrator.py`: сохраняет `independent.json` и `stage-one.json` **до первого
  чтения A/B**. Этап II начинается отдельной командой; проверяет хеш сохранённого
  результата, досье, реестра и конфигурации. Изменившиеся входы требуют нового этапа I.

Оба этапа используют `config.verifier` — отдельную настройку модели. Во втором
этапе нет истории первого вызова: только новый system/user и сохранённый результат.
Сопоставление обязано оценить каждую находку обоих аудиторов ровно один раз.
`model_independence_limited` указывает совпадение модели верификатора с моделью A/B;
разные модели также не гарантируют независимости обучения или юридической точности.
Первый этап запрашивает все девять направлений и новые обоснованные гипотезы без
квоты находок. Результат первого этапа не переписывается мнением второго.

## Запуск offline

Установка и Chromium — как в [README](../README.md). Дополнительных зависимостей нет.
Для примера с синтетическим недоступным сайтом:

```bash
lexradar analyze examples/analysis-dossier --output work/auditors
lexradar verify examples/analysis-dossier --registry examples/legal-registry.json \
  --output work/verifier-one
lexradar verify-compare examples/analysis-dossier --registry examples/legal-registry.json \
  --stage-one work/verifier-one --analysis work/auditors/analysis.json \
  --output work/verifier-final
```

Каталоги результатов должны быть новыми. Первый этап имеет `awaiting_comparison`;
окончание двух этапов — `complete`. Это завершение конвейера, **не** полнота
юридического обследования. Offline без ключа и сети выдаёт прозрачные placeholders:
не выполняет независимый LLM-поиск и не имитирует юридические выводы. Детерминированные
правила могут выявить некорректное основание исходной гипотезы. Пример результата:
[verification-offline.json](../examples/verification-offline.json).

## Реальный OpenRouter: два отдельных утверждения

Скопируйте [verifier-config.json](../examples/verifier-config.json), замените модель
на конкретный ID, настройте цены, токены и бюджет. Наследуемые поля A/B нужны только
для совместимости транспорта и имеют значения `unused/*`; запросы выполняются
исключительно с `verifier`. API-ключ задаётся только в `OPENROUTER_API_KEY`.
Никаких платных запросов в разработке/CI нет.

```bash
lexradar verify-preflight work/audit --registry work/legal-registry.json \
  --config work/verifier-config.json --output work/review-one
```

Человек просматривает **весь** `packet.json` и `preflight.json`, затем вручную
заполняет неподтверждённый `approval.json`: точный `packet_sha256`, `approved: true`,
`contents_reviewed: true`, `reviewer`, `approved_at` с часовым поясом. Эвристический
поиск ПДн не гарантирует их отсутствие. Подозрение блокирует передачу даже при
утверждении человеком. Общий флаг не обходит скрининг или привязку к SHA-256.

```bash
lexradar verify work/audit --registry work/legal-registry.json \
  --config work/verifier-config.json --output work/verifier-one --mode openrouter \
  --allow-external-transfer --packet-approval work/review-one/approval.json
lexradar verify-preflight work/audit --registry work/legal-registry.json \
  --config work/verifier-config.json --stage-one work/verifier-one \
  --analysis work/auditors/analysis.json --output work/review-two
```

Второй пакет содержит исходные материалы, нормы, сохранённый самостоятельный
результат и оба результата A/B; его SHA-256 другой. Просмотрите и отдельно утвердите
`work/review-two/approval.json`. Разрешение этапа I, как и разрешение v0.3, его не заменяет.

```bash
lexradar verify-compare work/audit --registry work/legal-registry.json \
  --config work/verifier-config.json --stage-one work/verifier-one \
  --analysis work/auditors/analysis.json --output work/verifier-final --mode openrouter \
  --allow-external-transfer --packet-approval work/review-two/approval.json
```

Проверки повторяются перед каждой попыткой. Хешируется точный UTF-8 user-пакет;
версия и хеш system-промпта записываются отдельно. Пакет — неизменяемый снимок;
изменение его состава после утверждения блокирует передачу. Локальные snapshots и
отчёты могут содержать чувствительные данные; храните их в защищённом `work/`, вне Git.
Утверждение пакета разрешает только передачу; **не** подтверждает юридические находки.

Бюджет обоих этапов переносится из сохранённого состояния. До попытки резервируются
верхняя оценка входных токенов по UTF-8 размеру и максимальный output; неизвестная
стоимость сохраняет резерв. Повторы ограничены, fallback/redirect запрещены.
Бюджет относится к последовательности этапов, не к общему счёту OpenRouter; отдельные
запуски и повторные ручные запуски могут оплачивать новые запросы. Жёсткий лимит ключа
необходим для потолка счёта провайдера. Журнал содержит безопасные метаданные и usage,
не API-ключ, сырые запросы/ответы или тела ошибок провайдера.

## Legal Source Registry

Реестр — JSON `SourceRegistry`, расширяемый добавлением `LegalSource` с уникальным ID:
название/номер НПА, отдельная предметная область, статья/часть/пункт, редакция,
`effective_from`/`effective_until`, `checked_at`, URL, `norm_text`, SHA-256 точного
UTF-8 текста, статус, способ проверки, проверяющий, основания проверки редакции и
происхождение. Текст сохраняется непосредственно в JSON; изменение без обновления
хеша отклоняется. Изменение реестра меняет пакет и требует нового утверждения.
LLM может ссылаться на ID, но не добавлять записи или менять доверенные поля.

Разделены `personal_data` (152-ФЗ), `medical` (323-ФЗ), `consumer` (2300-1),
`paid_medical` (ПП №736) и `other`. Совпадение известного номера с неверной областью
отклоняется. Несколько лиц сайта остаются отдельными `entity-0001`, `entity-0002`, …;
найденное название/ИНН не делает личность оператора подтверждённой.

`current_confirmed` означает подтверждение редакции **для периода сбора досье**.
Требуется локальная человеческая проверка официального HTTPS-источника из ограниченного
списка доменов портала правовой информации, непустой текст, корректный хеш, дата
действия, свежая дата проверки и документированные основания проверки редакции.
Давность — `legal_recheck_days` (по умолчанию 30, максимум 90). Подтверждение даты
публикации исходного закона само по себе не является проверкой актуальной редакции:
проверяющий обязан исследовать применимые изменения и переходные положения.

Состояния:

- `current_confirmed`: локально подтверждена действующая в проверяемый период редакция;
  применимость к оператору оценивается отдельно.
- `unverified`: источник/редакция не подтверждены, запись устарела, источник коммерческий,
  метод LLM, будущая дата или конфликт одновременно действующих редакций.
- `repealed`: подтверждённая редакция вне срока действия для проверяемого периода.
  Историческая редакция с доказанным интервалом может подходить для старого досье.
- `unavailable`: источник недоступен, подтверждения нет.
- Применимость результата: `unestablished`, `confirmed` или `not_applicable`.

**В поставляемом примере реально проверенных НПА нет.** Четыре записи — явно
неподтверждённые шаблоны с пустым текстом, неизвестной редакцией/датами и ссылкой на
главную страницу портала, не на полученную норму. Государственные источники не входят
в разрешённые назначения сети этой среды; автоматическое получение не выполнялось.
Нет имитации через поисковую выдачу, коммерческие публикации или придуманный текст.
Тестовые «подтверждения» используют только синтетические фикстуры и не являются НПА.

## Когда возможен verified_issue

По умолчанию любая LLM-находка — предложение. Для подтверждения нужны одновременно:

1. Проверенные артефакты, доступная точная цитата и исследованный текстовый фрагмент.
   В этом MVP подтверждается положительное наблюдение `present` в `text_excerpt`;
   отсутствие по всему сайту или неполному документу не подтверждается.
2. Все связанные нормативные записи имеют `current_confirmed`; нет конфликтов редакций.
3. Человек подтверждает факт, юридическую интерпретацию, идентичность конкретного
   оператора, вид деятельности, применимость и проверяемый период.

После изучения `independent.json` и реестра можно подготовить JSON-массив
`HumanFindingReview` и передать `--finding-reviews work/finding-reviews.json` в
`verify-compare`. Структура генерируется через `HumanFindingReview.model_json_schema()`.
Запись включает `packet_sha256` этапа I, `candidate_sha256` (SHA-256 канонического
JSON кандидата: `ensure_ascii=False`, `sort_keys=True`, separators `(',', ':')`),
проверяющего/время, `fact_verified`, `interpretation_verified`, применимость,
`operator_ref`, `operator_identity_verified`, источники идентификации, деятельность,
границы периода и мотивировку. Другая находка, другой пакет, лицо или период блокируют
использование записи. Это доверенный локальный ввод, не аутентифицированная подпись.

Для A/B `verified_issue` возможен только при точном совпадении факта, интерпретации,
структурированного утверждения, evidence ID и подтверждённых норм с независимо
подтверждённой находкой. Непроверенные правовые основания нельзя «подтвердить»
совпадением мнений. Неустановленная применимость остаётся гипотезой; доказанная
неприменимость даёт `rejected` с объяснением.

## Полнота и ограничения

Для каждой страницы/документа отчёт содержит ID, URL, тип, известное количество
страниц, страницы с доступным текстом, реально заявленные исследованные номера,
доступность текста, необходимость визуальной проверки, состояние сбора и причины
неполноты. Исследование недоступной страницы отклоняется. Для PDF проверяются
цитаты конкретных доступных страниц; непрочитанные страницы исключаются. Любое
исследование PDF остаётся текстовым: рисунки и исходная вёрстка не просмотрены.
Оригинальный HTML и изолированные PNG не изображаются как просмотренный живой сайт.

`text_review_fraction` = число материалов с заявленной проверкой реально доступного
текста / число собранных материалов. При нуле материалов — `null`. Отдельно показаны
известные страницы PDF, исследованные текстовые страницы и документы с неизвестным
числом страниц. 100% этой метрики означает только охват собранного текста, а не всего
сайта, изображений, правовых обязательств или юридическую достоверность. Заявление LLM
о просмотре даже доступного текста нельзя доказать наблюдением внутренней работы модели.

Статусы находок: `verified_issue`, `potential_issue`, `rejected`,
`insufficient_evidence`, `no_issue_observed`. Последний ограничен цитируемой областью
и не означает полного соответствия. Ошибочное основание технической гипотезы может
быть отвергнуто без утверждения, что противоположный юридический вывод доказан.
Не требуются внутренние документы как универсальное условие любого вывода.

Остаются вне MVP: автоматическая актуализация всего законодательства, аутентификация
юриста и электронные подписи, OCR/визуальный анализ, подтверждение реестровой личности
оператора, полноценное доказательство отсутствия сведений, универсальное семантическое
сопоставление выводов, Gateway для GO и клиентская отправка. Подмена инструкции в
недоверенных данных ограничивается промптами и схемами, но не устраняется гарантированно.
