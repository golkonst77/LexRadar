# Один контролируемый прогон Control Center → EspoCRM

30.10.2026. Подготовка к ручной проверке; живой экспорт в этой работе не выполнялся.
Не отправлять письма, не назначать sendAt, не менять рабочий журнал вручную.

## Сначала сверка текущей Клиники «А»

Её web-account запись имеет старый общий draft HOLD без доказанного места
остановки. Код сохраняет этот HOLD даже после повторного подтверждения Account.
Это ожидаемый безопасный результат; сейчас успешное восстановление этой записи
одним нажатием не обещается.

В браузере EspoCRM открыть и сверить:

1. `http://192.168.233.105/#Account/view/6ae32c46426f8cdb3`:
   юридическое имя ООО «Клиника А», домен aclinic-krd.ru и подтверждённый
   адрес получателя. Другой Account выбирать или создавать нельзя.
2. `http://192.168.233.105/#Document/view/6ae32e009a0f5cc31`:
   связь с этим Account, файл `6ae32da53033facf1`. Скачать PDF и сравнить
   SHA-256 с PDF текущего READY в Control Center и сохранённым SHA-256 :draft
   записи журнала. Совпадение имени файла недостаточно.
3. `http://192.168.233.105/#Email/view/6ae3374166673d4cf`:
   Account, адресат, отправитель, утверждённое тело, статус Draft,
   отсутствие sendAt/cc/bcc, правильный PDF; скачать вложение и сверить SHA-256.
   Искать также дополнительные Document/Email этого Account, включая точные
   маркеры LexRadar из журнала; проверить отсутствие дублей.
4. Сохранить приватный результат сверки: фактические ID, хеши, статус,
   наличие/отсутствие дополнительных сущностей и время проверки. Если PDF
   изменился, оставить HOLD: известный старый Document код не заменяет.

Даже при совпадении объектов старый общий HOLD автоматически не снимается:
нужен отдельный разбор подтверждённых результатов и согласованное восстановление
привязки. Не удалять :draft, steps или draft_error, не менять lead ID ради повтора.
«Он Клиник Бэйби» с несколькими юрлицами остаётся HOLD_IDENTITY.

## Один живой прогон для допущенного READY без старого неопределённого HOLD

1. Запустить обычный Control Center с этим checkout привычным способом и открыть
   локальный адрес `http://127.0.0.1:8080` (либо настроенный порт).
   Исключить параллельное ручное создание записей этой организации в CRM.
2. В «Готовых предложениях» выбрать **одну** READY-организацию. Открыть её
   актуальный PDF, сверить организацию, сайт и email. Ничего не перегенерировать.
3. «Передать выбранные в CRM» → проверить предпросмотр → «Подтвердить поиск
   или создание Account». Получить ACCOUNT_VERIFIED, записать Account ID.
   При HOLD/HOLD_IDENTITY остановиться и сохранить причину.
4. Один раз нажать «Подготовить PDF и Email Draft». Дождаться ответа.
   При неопределённой ошибке не повторять кнопку вслепую: сохранить результат
   и сверить журнал/CRM. Код разрешает лишь восстановление по проверенным ID
   и маркерам, а неизвестный POST действия вложения остаётся HOLD.
5. При DRAFT_VERIFIED записать Account/Document/Email ID и открыть прямую ссылку
   на проверенный черновик. Проверить Draft, адресата, Account, отсутствие sendAt,
   тело и вложенный PDF; скачать PDF и сравнить SHA-256 с исходным.
   Обычная папка «Черновики» Admin может не показывать API-письмо: использовать
   прямую ссылку или «Эл. письма → Все» и поиск темы.
6. Без подтверждённого email допустим DOCUMENT_VERIFIED_NO_DRAFT: проверить
   Document; Email создаваться не должен. Не нажимать «Отправить» и не планировать
   отправку. Этим единственный живой прогон закончен.

Для Клиники «А» текущий допустимый результат — HOLD и описанная выше ручная
сверка. Другую организацию нельзя выбирать только ради обхода её блокировки.

## Что проверено локально

14 адресных unittest с FakeAPI и tempfile-журналами; py_compile трёх модулей;
self-check реального UI-обработчика без HTTP-сервера/сети: Host, Origin, CSRF,
неизвестный stage, устаревший lead, сопоставление стабильного ID, HOLD_IDENTITY,
GET preview без вызова подготовки. Рабочий журнал только читался; его SHA-256
после проверок совпал. Это не подтверждение реальной CRM или визуальной проверки.

Остаются ограничения: внешние писатели не защищены локальным flock; при
неполном поиске/неопределённом ответе требуется ручная сверка. Exporter для
известной Клиники «А» использует исторические ID и сверяет SHA-256; старый PDF
не заменяется новым. Только известный ручной Draft допускает прежнюю узкую
синхронизацию body после всех проверок — этот механизм не расширялся.
