# Конвейер существующих десяти организаций

Модуль `lexradar.pipeline10` использует `parser_import.convert`, реальный
`mvp_batch.run`, HTML/PDF из существующего утверждённого шаблона и `espo_export.run`.
Parser v3 не запускается, шаблоны не изменены. Платных вызовов в модуле нет.

Одна команда для обычного пользовательского SSH-терминала:

```bash
cd /home/golkonst/src/LexRadar-compact && PYTHONPATH=src /home/golkonst/src/LexRadar/.venv/bin/python -u -m lexradar.pipeline10 /home/golkonst/lexradar-batch10-20261029-g3YHX9/clinics.csv --allow-site-collection
```

Команда создаёт новый приватный `/home/golkonst/lexradar-pipeline10-<UTC-время>`.
Вывод одновременно идёт на экран и в `pipeline-*.log`, без внешнего tee.
Сохраняются исходный CSV, `report.json`, `results.csv`, `summary.json`,
`approval-template.json`, отдельные каталоги аудита. Каждая строка получает
READY/REVIEW/HOLD/ERROR; ошибка строки не останавливает остальные.
Код выхода 0 означает все READY, 1 — есть REVIEW/HOLD/ERROR, 2 — неверный вход/хранилище.

Локальный аудит не требует CRM. Только явный `--check-crm` либо
`--confirm-create-drafts` включает GET Metadata/поиск Account; недоступность CRM
не препятствует сбору и сохранению PDF. Конфликт Account сохраняет PDF, но даёт
HOLD. При ошибке API новые обращения блокируются. Без CRM duplicates учитывает
только повторные домены CSV; совпадения с CRM неизвестны.

Используется прежний `mvp_batch.run(mode="prepare")`: express-screening-144,
до 7 HTML, 2 документов, 16 запросов, 60 секунд, static_only, AI-вызовов 0.
Robots, same-origin, правила 1/2/3/5 и шаблон не менялись. Имя адресата остаётся
нейтральным до подтверждения личности; email из CSV сохраняется во входе аудита.
КП по утверждённому шаблону при наличии триггера получает REVIEW: необходимо
проверить содержание, включая постоянный блок 4. Это существующее КП, а не
отдельный технический шаблон. Допуск к CRM по-прежнему требует saved-аудит и
независимый legal_review; флаги подтверждения не заменяют эти проверки.
Нет подтверждённых оснований/материалов — HOLD; это не заключение о соответствии сайта.

Терминал и audit-summary.json показывают число полученных/полностью прочитанных
страниц, ограничения чтения, ошибки сбора и ID триггеров. Сохраняется штатный
heartbeat сбора каждые 30 секунд. Финальные счётчики:
`audit_success` — проверен пакет доказательств, `proposal_eligible` — штатный
движок сформировал КП, `PDF`/`full_PDF` — PDF из полного утверждённого HTML прошёл
техническую проверку, `production_qualified` — saved-путь дал GO. Ни один из этих
счётчиков не означает разрешение отправки. REVIEW/HOLD/ERROR, duplicates и
CRM_Drafts выводятся отдельно. Проверка PDF: сигнатура, размер, страницы,
извлекаемый текст и SHA-256; визуальную проверку оператором она не заменяет.

## Продолжение после проверки

Повторять ту же команду с `--output /абсолютный/каталог/из/первого/вывода`.
Весь конвейер блокируется flock; CSV в каталоге должен совпадать. Завершённый
аудит переиспользуется через штатный resume с проверкой снимка файлов.
Незавершённое состояние требует проверки; не удалять файлы ради обхода HOLD.

Скопировать `approval-template.json` в отдельный `approvals.json`. Объект индексирован
стабильными Parser ID. Для конкретной строки:

1. Проверить юридическую личность и связь с сайтом; только затем указать
   `identity_verified: true`. Поля company_name/website/email должны совпадать
   с кандидатом; исправление исходных контактов требует отдельной сверки,
   автоматической подмены адресов из CRM нет.
2. Указать абсолютные пути `analysis` к существующему реальному Single A
   `analysis.json` и `dossier` к соответствующему пакету. Без них нет AI-аудита.
   Если анализа нет, нужен отдельный разрешённый операторский запуск:
   `lexradar audit` с просмотром пакета и интерактивным подтверждением платного
   запроса/передачи. Конвейер не даёт это разрешение за оператора.
3. Добавить к команде `--approvals /абсолютный/approvals.json`. Режим saved
   проверяет привязку анализа и создаёт `legal-review-template.json` в каталоге
   saved-аудита. Заполнить отдельную копию специалистом и указать её абсолютный
   путь в `legal_review`. Штатный qualify проверяет хеши, источники права,
   применимость и предмет услуги; отрицательные решения не обходятся.
4. После повторного saved-прогона прочитать персональный PDF, проверить внешний
   вид и содержание. Указать его точный `pdf_sha256` из report.json,
   `export_approved: true`; `recipient_verified: true` только для независимо
   проверенного адреса. При существующем ручном документе указать
   `existing_document_id` после сверки; при необходимости также segment и
   industry_verified по правилам экспортёра.
5. Для одобренных строк добавить `--confirm-create-drafts` к той же команде.
   Без этого флага записей нет. Экспортёр использует общий постоянный журнал
   `~/.local/state/lexradar/espo-export.json`, создаёт/переиспользует сущности,
   проверяет связи, байты PDF и Draft повторным GET. READY означает только
   DRAFT_VERIFIED. Отсутствие подтверждённого email может дать Document без Draft
   и итоговый HOLD. Нет sendAt или разрешения на отправку.

Не менять ID и не очищать журнал. При повторе в новом каталоге другая генерация
PDF под прежним ID приводит к HOLD, а не к повторному созданию документов.
Локальный flock не защищает от сторонних писателей CRM; это ограничение
существующего экспортёра сохраняется.
