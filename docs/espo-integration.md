### Безопасность повторов Control Center, 30.10.2026 (текущее правило)

Этот раздел заменяет прежний допуск по общей ошибке `Previous draft failure`.
Первый `Account binding changed` возникал из-за разного сравнения кавычек:
Prepare нормализует имя, Exporter требует точное имя CRM. Перед экспортом
сохранённый Account проверяется по ID, нормализованному имени и домену,
затем используется точное имя CRM. Перепривязки к другому Account нет.

Общая ошибка после повторного HOLD утратила доказательство места остановки.
Пустые steps не доказывают отсутствие CRM-записей. Старый общий HOLD остаётся
заблокированным, включая текущую запись Клиники «А»; повтор Account его не снимает.
Только исходный одиночный `Account binding changed` с прежними дополнительными
проверками допускает исправление эквивалентного написания draft binding.
Первый отказ новых попыток дополнительно сохраняется в `draft_failure`.

Связь Document проверяется полным списком Account: только сохранённый Account;
лишняя связь или неполный ответ дают HOLD до создания Email.

Новые попытки отмечаются `resume_protocol=1` в прежней :draft записи до вызова
Exporter. Повтор проходит все проверки Account/binding/template/PDF и использует
прежние durable steps и точные маркеры. Незавершённая старая попытка без этого
признака требует сверки. Перед POST создания намерение сохраняется атомарно;
потеря ответа/сбой записи ID возможны, поэтому сначала ищется точный маркер.
Нет однозначного результата поиска — HOLD без повторного POST.

В существующем Exporter точечно добавлен durable step `email_attachment`:
намерение до `POST Document/action/getAttachmentList`, ID до PUT Email.
Сохранённое вложение проверяется по sourceId, имени и SHA-256; неизвестный
ответ действия блокирует повтор POST. Успешный PUT с потерянным ответом
восстанавливается чтением Email. Схема API не менялась: getAttachmentList →
attachmentsIds → GET Email и SHA-256. Только Draft, без sendAt и отправки.

Выбранный email новых веб-подтверждений фиксируется в `draft_contact` на этапе
Account; изменение требует HOLD. Без email — DOCUMENT_VERIFIED_NO_DRAFT.
Сохранённые ID при HOLD показаны для сверки, а не как подтверждение успеха.
Операторская процедура: [один контролируемый прогон](crm-controlled-run.md).
Локально: 14 адресных unittest с фейковым API/временным журналом, py_compile
и self-check обработчика UI (Host/Origin/CSRF, stage, READY-выбор/lead ID,
HOLD_IDENTITY, GET без экспорта). Живого API и записи рабочего журнала не было.
Реальная передача Document/Email ещё требует живой проверки оператором.

Операторский маршрут для уже собранного Parser CSV из 10 строк:
[pipeline10](pipeline10.md). Он вызывает существующий экспортёр с тем же
журналом и явными одобрениями; технический prepare-PDF не допускается к экспорту
без реального сохранённого аудита, независимого legal_review и проверки PDF.
Массовая живая запись этим маршрутом пока не проверена.

Из текущего checkout, один операторский JSON/CSV-манифест и один постоянный журнал:

```bash
# PREVIEW: без запросов в CRM
./espo-export /absolute/path/approved-manifest.json
# Создание после проверки оператором
./espo-export /absolute/path/approved-manifest.json --confirm-create-drafts
```

Минимальная запись JSON (манифест — массив записей):

```json
[{
  "id": "proposal-2026-001",
  "company_name": "Название организации",
  "website": "https://example.invalid",
  "email": "recipient@example.invalid",
  "phones": ["+79991112233", "+79994445566"],
  "pdf_path": "ready/proposal.pdf",
  "recipient_verified": true,
  "export_approved": true
}]
```

Путь PDF относителен манифесту или абсолютный. Это уже готовый одобренный PDF:
экспортёр не генерирует и не меняет его. Лимит 10 MiB, проверка `%PDF-` и SHA-256.
CSV поддерживает те же поля; `phones` — номера через `;`, флаги — `true`.
Отрасль при наличии: `segment` и `industry_verified: true`. Значение проверяется
по enum cSegment из Metadata. Для новой карточки без отрасли выбирается только
допустимая пустая категория или «Не определено»; если их нет — HOLD, чтобы не
унаследовать ошибочный default «Франшизы». Глобальные настройки не меняются.

Account ищется по точному имени и нормализованному домену (www/http/https не
мешают). Конфликт или неоднозначность — HOLD. Email заполняется только при
recipient_verified; существующий email не затирается. Телефоны дополняют
phoneNumberData при Metadata type=phone, основной сохраняется. Иначе дополнительные
номера сохраняются в описании. Существующая категория не перезаписывается.
Дозаполнение Account использует PUT; существующий Document не изменяется.

Document создаётся с publishDate и accountsIds. Связь обязательно читается через
GET Document/{id}/accounts: наличие accountsIds в GET Document не требуется.
PDF скачивается и проверяется SHA-256. Для Email создаётся отдельный Attachment
тех же байтов; проверяются Draft, to/from, parent Account и вложение.

Универсальный утверждённый текст хранится в `src/lexradar/espo_email.json`,
входит в пакет. Тема «Коммерческое предложение для {company_name}» персонализируется;
текст сохраняется дословно. Технический маркер добавляется только к теме.
`--template` остаётся для явно одобренного альтернативного JSON name/body/isHtml.
Тема чужой клиники из API больше автоматически не копируется.

Пустой или неподтверждённый email не блокирует Account/Document:
`DOCUMENT_VERIFIED_NO_DRAFT` с причиной, без Email. Неверный непустой адрес — HOLD.
Публикация адреса на сайте и recipient_verified **не означают разрешение на
рекламную отправку**. DRAFT_VERIFIED также не разрешает отправку.
Нет sendAt, SMTP, отправки, изменения mailer/очереди/расписания.

## Ранее созданные объекты и повторные запуски

Для ручного Document укажите `existing_document_id`: экспортёр проверит Account
через связь и SHA-256 вложения, не создавая новый Document/PDF. Если у Account уже
есть документы, а привязка не указана и в журнале нет этапа, экспорт остановится
для сверки. Встроенных ID для отдельных доменов нет. Ручной Email не выбирается
автоматически; сохранённый Draft проверяется через прежние steps и маркеры,
несовпадение полей даёт HOLD без исправления тела.

Журнал: `~/.local/state/lexradar/espo-export.json`, можно указать `--journal`.
Все запуски используют один журнал; flock, атомарная запись, fsync, права 0600.
Перед POST сохраняется намерение, после — ID и GET-проверка. Неопределённый POST
восстанавливается по точному маркеру; если восстановление невозможно — HOLD без
повторного POST. Изменение PDF, получателя, компании или шаблона под прежним id
даёт HOLD. Не удаляйте журнал и pending для обхода проверки. Параллельные внешние
писатели CRM локальной блокировкой не защищены: абсолютной гарантии от дублей нет.

Старые манифесты остаются читаемыми; необязательны phones/segment/existing_document_id.
Старые записи журнала с прежним шаблоном остановятся на Template changed:
используйте прежний утверждённый `--template` для проверки завершённого экспорта;
не меняйте ID и не очищайте журнал ради обхода. Незавершённые старые Document без
связи требуют ручной сверки, автоматического изменения таких документов нет.
После DOCUMENT_VERIFIED_NO_DRAFT добавление проверенного email под прежним ID также
требует явной сверки журнала оператором, поскольку получатель является частью привязки.

API фиксирован: http://192.168.233.105/api/v1/, редиректы запрещены. Ключ из
ESPO_API_KEY либо ~/.config/lexradar/espo.env; секреты и тела ошибок не выводятся.
Metadata проверяется перед записью. PREVIEW проверяет только локальные данные,
не схему/права/конфликты CRM. HOLD даёт код 1, ошибка манифеста/журнала — 2.

GET-проверка образца (не подтверждает загрузку):
`./espo-export --check-connection /absolute/private/output-dir`.
Сохраняет приватные sample.json/template.json; тему образца нельзя переносить другому клиенту.

Локальная проверка:
`PYTHONPATH=src python3 -m unittest discover -s tests -p test_espo_export.py -v`.
В этой среде живой GET Metadata недоступен; POST/PUT не выполнялись. Проверены
моки и безопасный PREVIEW `examples/espo-export/manifest.json`; этот фиктивный
пример нельзя запускать с подтверждением на боевой CRM.

## CRM_PREPARE_ONLY — отдельная подготовка REVIEW, 29.10.2026

`./crm-prepare-only` сохраняет Account, готовый PDF и доступные файлы досье
как Document/Attachment, текст будущего письма — только в Note типа Post.
Email, Email Draft, send и sendAt не используются. Строгий `espo-export`
не изменён; legal_review и GO для этого отдельного маршрута не требуются.

Манифест — JSON-массив с полями `id`, `company_name`, `website`, `pdf_path`,
`pdf_sha256`, `dossier`, `letter_text`, `identity_verified` (boolean).
Пути относительны манифесту или абсолютны. Сайт и точное проверенное название
образуют привязку организации. Запись требует `identity_verified: true`;
это подтверждение оператора, не автоматический вывод из Parser CSV.
Непроверенный email игнорируется и не мешает сохранению материалов.

Подготовлен приватный манифест контрольных четырёх REVIEW-комплектов:
`/tmp/lexradar-crm-prepare/manifest.json`. В нём подтверждение личности оставлено
false: отчёт партии не содержит такого подтверждения. После проверки оператор
указывает точное имя существующего Account и true; в частности, у контрольной
«Клиники А» название в отчёте отличается от ранее известного ООО «Клиника А».
Конфликт даёт HOLD, без изменения старого Document и без дубля Account.

```bash
# Только локальная проверка готовых файлов, без CRM API:
./crm-prepare-only /tmp/lexradar-crm-prepare/manifest.json --journal /tmp/lexradar-crm-prepare/journal.json --output /tmp/lexradar-crm-prepare/dry-run.json
# После подтверждения личности в манифесте; эта команда сейчас НЕ выполнялась:
./crm-prepare-only /tmp/lexradar-crm-prepare/manifest.json --confirm-prepare-crm --output /tmp/lexradar-crm-prepare/crm-result.json
```

Постоянный журнал записи по умолчанию:
`~/.local/state/lexradar/crm-prepare.json` (отдельный от строгого экспортёра).
Не удалять и не менять журнал для обхода конфликтов. Он использует flock,
атомарную запись, fsync и намерение до POST; неизвестный результат POST не
вызывает слепое повторное создание. Маркеры и GET проверяют объект, связь и SHA-256.
Существующие Documents не перепривязываются. Параллельные внешние писатели CRM
по-прежнему требуют организационного исключения гонки создания Account.

Результат по строкам содержит PENDING_REVIEW (также внутри Note), ID, SHA-256,
ошибки и перечень пропущенных материалов. Неподдерживаемый файл не останавливает
остальные: сохраняются PDF и Note со списком локальных доказательств и ошибок.
Неудачные материалы фиксируются как skipped и автоматически не перезагружаются;
для их восстановления нужна ручная сверка журнала. Недоступность обязательного
Note/Account или PDF даёт HOLD, уже созданные объекты сохраняются в журнале.
Статус PENDING_REVIEW с ошибками требует просмотра пропущенных вложений.
Нет нового enum в CRM: статус хранится в Note и локальном отчёте.

Dry-run партии: 4 PREVIEW, 4 PDF и 53 файла досье. Аудит и генерация PDF
не повторялись. Реальная схема Note и права на загрузку произвольных типов
в этой CRM не проверены: живых API-запросов не было.

### Минимальный CRM_PREPARE_ONLY, 29.10.2026 (заменяет требования выше)

Ошибки чтения дополнительных материалов дают warnings и не блокируют проверенный
PDF. Ограничение 10 MiB относится к PDF, а не к локальным доказательствам.
Note — дополнительный Post с текстом письма: при HTTP 403 пропускается с отдельным
warnings `Note skipped`, без повторного POST после отказа чтения. Отсутствие схемы
Note также даёт предупреждение. Прочие ошибки Note требуют сверки (HOLD).
Email, Draft, send и sendAt не используются. Строгий экспортёр не менялся.

Сохранены binding и маркеры прежнего журнала для читаемых прежних материалов;
Account/PDF/Document восстанавливаются и проверяются без повторного создания.
Старые skipped дополнительных вложений не загружаются повторно и не дают HOLD.
Неопределённый POST PDF без восстановимого ID по-прежнему требует сверки.
Существующие объекты не удаляются и не перепривязываются.

### Автоматическая идентификация CRM_PREPARE_ONLY, 29.10.2026

Заменяет обязательное ручное выставление identity_verified: подготовка читает
collection.json и сохранённые HTML/TXT, проверяет исходный SHA-256 и точное
соответствие текста. Допуск: тот же нормализованный домен (поддомены раздельны),
единственное юридическое имя с контекстом владельца/оператора сайта и точное
совпадение имени либо его части без организационной формы. Кавычки, регистр и
