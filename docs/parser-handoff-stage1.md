# Parser v3 → LexRadar → EspoCRM: этап 1

Адаптер: `PYTHONPATH=src python3 -m lexradar.parser_import`. Только стандартная
библиотека; Parser, mailer и существующие CLI не изменены. Нет сетевых запросов,
AI, POST/PUT, отправки или изменения расписания. `--dry-run` явно обозначает
этот единственный режим: локальные приватные файлы создаются.

## Запуск из обычного терминала

Из `/home/golkonst/src/LexRadar-compact`:

```bash
umask 077
PYTHONPATH=src python3 -m lexradar.parser_import \
  /home/golkonst/parser-smoke-20261029/clinics.csv \
  --sqlite /home/golkonst/parser-smoke-20261029/data.db \
  --data-root /home/golkonst/lexradar-data --dry-run
```

Каталог данных создаётся с правами 0700; существующий общедоступный каталог
отклоняется. Файлы имеют права 0600. Данные внутри текущего Git checkout и
символические ссылки в пути каталога назначения запрещены. Старые `runs-*`
и архивы не используются и не изменяются. Не добавляйте каталог данных в Git.

В выводе только путь, число строк и статусы. Каталог запуска имеет имя
`parser-<полный SHA-256 исходного CSV>`. Он содержит:

- `parser.csv`: исходные байты, включая BOM и все 24 исходные колонки;
- `parser.sqlite`: согласованный SQLite backup с committed WAL, проверенный
  через `integrity_check`; это снимок базы, а не побайтовая копия файла БД;
- `lexradar.csv`: фактический формат `mvp_batch.read_csv`: url, company_name, email;
- `crm-candidates.json`: контакты и сведения Parser для ручной подготовки CRM;
- `import.json`: идентификатор запуска, SHA-256 файлов и `NOT_EXPORTED`.

Скрининг Parser не становится юридическим выводом. Для аудита используется
нейтральное название сайта с явной оговоркой о неподтверждённой связи с
организацией. Email входа аудита всегда пуст: исходный адрес, если он есть,
остаётся только в приватном кандидате CRM. Даже подтверждение бренда Parser
не удостоверяет юридического оператора сайта.

## Существующий конвейер и будущий рабочий запуск

Подставьте путь `run` из вывода адаптера. Интерпретатор другого checkout здесь
используется только ради установленных зависимостей; `PYTHONPATH=src` выбирает
код текущего LexRadar-compact, без изменения другого репозитория.

```bash
RUN=/home/golkonst/lexradar-data/parser-$(sha256sum /home/golkonst/parser-smoke-20261029/clinics.csv | cut -d ' ' -f 1)
PY=/home/golkonst/src/LexRadar/.venv/bin/python

# Будущий ограниченный GET-сбор одного сайта и подготовка черновика/PDF.
# Это отдельный рабочий шаг, не dry-run; в рамках этапа 1 не запускался.
PYTHONPATH=src "$PY" -m lexradar.mvp_batch "$RUN/lexradar.csv" \
  --output "$RUN/audit" --mode prepare --max-sites 1 --allow-site-collection

# Продолжение того же запуска: те же вход и параметры, без нового output.
PYTHONPATH=src "$PY" -m lexradar.mvp_batch "$RUN/lexradar.csv" \
  --output "$RUN/audit" --mode prepare --max-sites 1 --allow-site-collection --resume
```

`prepare` уже собирает технические материалы без LLM, применяет существующие
правила и создаёт HTML/PDF только при наличии соответствующих оснований.
PDF требует работоспособного Chromium. Сбор/PDF могут закончиться HOLD/SKIPPED;
отсутствие PDF или сигналов не означает соответствия закону. Проверяйте
`audit/manifest.json`, `results.csv`, `sites/*/review.json` и исходные доказательства.
Все технические результаты останутся внутри внешнего каталога запуска.

Повтор импорта проверяет сохранённые файлы, возвращает `reused=true` и ничего
не перезаписывает. Изменение SQLite при неизменном CSV или повреждение файлов
даёт HOLD: сохранённый запуск нужно разобрать вручную. Новый CSV даёт новый
запуск; стабильный ID кандидата зависит от точных имени организации и URL,
а не от номера строки/рейтинга/контактов. Это не глобальная дедупликация:
изменение имени, схемы URL или домена может изменить ID. Совпадающие строки
организация+URL отклоняются; сайты нескольких филиалов существующий batch
может пропускать как `duplicate_url` — проверьте результаты перед CRM.

## CRM и mailer

Кандидат CRM допустим без Email, но **нынешний `espo-export` не умеет создавать
только Account**: он требует проверенный Email, PDF и оба явных одобрения для
связки Account + Document + Email Draft. Поэтому пустой Email не мешает аудиту
и подготовке карточки, но реальная запись такой карточки остаётся отдельным
согласованным ручным шагом или будущим небольшим дополнением экспортёра.
Автоматического обхода блокировки/выдуманного адреса нет.

`crm-candidates.json` — очередь проверки, не утверждённый манифест экспорта.
Все одобрения false, PDF пуст, статус всегда NOT_EXPORTED. Наличие любого
email также не разрешает рассылку. После ручной проверки личности, адресата,
аудита и PDF оператор отдельно готовит утверждённый манифест по
[существующей инструкции](espo-integration.md), используя стабильный `id`.

До первой записи необходимы отдельное согласование, успешное GET-чтение CRM,
проверка схемы/прав, конфликта организации, PDF и утверждённого текста.
Для проверки только чтения из обычного терминала:

```bash
./espo-export --check-connection /home/golkonst/lexradar-data/crm-readonly
# Локальный preview уже вручную подготовленного манифеста, без API:
./espo-export /absolute/path/approved-manifest.json \
  --journal /home/golkonst/lexradar-data/espo-export.json
```

Для будущей согласованной записи используйте тот же существующий экспортёр,
один постоянный журнал `espo-export.json` и процедуру из его инструкции.
У него уже есть intent до POST, восстановление по маркерам и проверка GET после
записи; неопределённый результат даёт HOLD без повторного POST. Не менять ID,
не очищать журнал и не считать preview подтверждением CRM-записи.

Mailer `/home/golkonst/lexradar-mailer/mailer_v2.py` принимает ID существующих
Email Draft, а не Parser CSV. Его preview читает CRM, но также пишет локальный
журнал; он здесь не запускался. Его config, approved, batch и расписание
не изменены; подключение адаптера к планировщику не требуется на этапе 1.

  Причина недоступности не установлена; успешного чтения или записи нет.
