# Операторский аудит LexRadar

Команды запускаются из корня проекта в обычном серверном окружении с сетью.
`lexradar` — существующий entrypoint; также доступен `python -m lexradar`.
В локальном окружении этой задачи: `PYTHONPATH=src /tmp/lexradar-029-venv/bin/python -m lexradar`.
Системные пакеты для этого задания не устанавливались.

## Бесплатная подготовка

```bash
lexradar audit https://example.ru/ --output runs/example-prepare --cookie-check
```

По умолчанию AI не вызывается. Сбор ограничен 40 страницами, 20 PDF, 100
запросами, 600 секундами, интервалом не менее 2 секунд (robots может увеличить),
5 MB на файл и 50 MB всего. Работают robots, TLS, DNS/IP pinning и same-origin.
При недоступном браузере нет скрытого повторного сбора. Для отдельного запуска
без визуальных доказательств есть явный `--static-only` с теми же сетевыми защитами.

Досье копируется, тексты воспроизводятся из оригиналов. Если весь пакет больше
200000 байт, целые источники выбираются в порядке политика → согласие → реквизиты
→ лицензия → запись → контакты → остальные. Текст не обрезается. Исключения
сохраняются в selection.json и предупреждении пакета. Это эвристика, а не
подтверждение полной проверки сайта. Артефакты полного сбора остаются локально.
Если не получено ни одного доступного доказательства, платный этап блокируется.

`--cookie-check` сохраняет cookie-inspection.json: признаки Метрики/GA/GTM/других
интеграций, ссылки ресурсов, дословные фрагменты cookie-текста, статические
элементы возможного согласия/отказа/настроек с URL и хешем HTML. Это анализ
всего указанного исходного досье, даже если часть страниц не вошла в AI-пакет.
Наличие разметки не доказывает запуск аналитики, установку cookies или видимость
баннера. Все динамические проверки остаются NOT_VERIFIED.

Живой JavaScript здесь намеренно не включён: существующий изолированный
сборщик отключает скрипты и блокирует подзапросы. Включение JS/внешних ресурсов
не обеспечит SSRF-защиту для всех сетевых каналов браузера. Для будущего отдельного
динамического этапа нужен ограниченный browser worker с принудительной сетевой
изоляцией, robots и лимитами каждого запроса; его в этой версии нет.

## Один платный запрос — только отдельное разрешение

Пример команды для оператора, **не выполнявшийся в задании №102**:

```bash
lexradar audit https://example.ru/ --dossier runs/example-prepare/dossier \
  --output runs/example-ai --paid --allow-external-transfer --cookie-check
```

Ключ должен уже находиться в переменной окружения OPENROUTER_API_KEY. CLI не
ищет и не печатает ключи, не вызывает API проверки баланса. Запускается один
Single A запрос GPT-5 Mini, reasoning low, max_tokens 28000, timeout 120 сек.,
retries 0, provider fallback запрещён. Бюджет $0.50 с резервированием по caps;
провайдер не гарантирует абсолютного внешнего потолка списания.

Перед запросом оператор должен локально прочитать preflight/packet.json и
preflight/preflight.json, назвать себя и ввести точную фразу с SHA-256 и бюджетом.
Без --paid нет запроса. Скрининг ПДн блокирует передачу при подозрениях.
Только явно выбранный --mvp-no-screening и дополнительная фраза «БЕЗ СКРИНИНГА ПДн»
разрешают диагностическую передачу просмотренного пакета. Это отключает только
скрининг передачи, а не целостность, цитаты, бюджет, коммерческий отбор или
запрет отправки клиентам. Не подтверждайте просмотр, если пакет не прочитан.

events.jsonl и терминал показывают этапы, длительность, модель, промпт, размер,
отправку, пассивное ожидание каждые 10 секунд, usage/стоимость, валидацию,
коммерческий отбор и сохранение. Heartbeat не создаёт запросов. Ошибка/timeout
не повторяется; при неизвестной стоимости резерв сохраняется, а возможное
списание отмечается отдельно. Не запускайте новую платную команду автоматически.

## Офлайн-перепроверка сохранённого ответа

```bash
lexradar audit https://business.example.invalid/ --dossier runs-101/dossier \
  --saved-audit runs-101/audit --output runs/example-replay --cookie-check
```

Ключ и разрешение передачи не нужны. Оригинал, журнал usage и исторический
analysis.json сохраняются; повторная валидация пишет новый производный результат.
new_ai_calls=0, new_ai_cost_usd=0. Исторические расходы не маскируются под новые.
Все каталоги output должны быть новыми. Исходные досье/аудиты не изменяются.

## Три независимые оси оценки

assessment.json — новый sidecar schema_version=102, старый AnalysisReport 0.3
не мигрируется и остаётся читаемым. Для каждой цитаты сохраняются объявленная
привязка, статус и все реальные совпадения с URL/evidence_id/страницей/смещениями.
MATCH, NOT_FOUND, WRONG_SOURCE и BAD_OFFSETS различаются. WRONG_SOURCE показывает
альтернативные первоисточники, но автоматически не переписывает цитату.
Повтор cookie-текста на разных страницах не считается неоднозначностью факта
наличия цитаты. Legacy exact_locations сохраняет требование единственного span.

Фактические состояния:
- CONFIRMED: полное поле fact является точной цитатой и есть независимое совпадение.
  Это подтверждение текстового наблюдения, не реального поведения сервера.
- PARTIAL: есть точные цитаты, но весь fact — пересказ/составное утверждение.
- UNSUPPORTED: нет точной цитаты в объявленном источнике.
- CONTRADICTED: независимый оператор явно зафиксировал противоречие и привёл
  проверенную дословную контрцитату. Автоматического семантического вывода нет.

Юридическая классификация отдельно: confirmed_violation,
confirmed_fact_with_legal_risk, justified_hypothesis, unsubstantiated_assumption,
positive_fact. Ни AI, ни совпадение цитаты не устанавливают нарушение.
confirmed_violation допускается только при локальном независимом подтверждении
с источниками права; это декларация проверившего специалиста, не онлайн-проверка
актуальности закона программой. Положительное наблюдение не становится дефектом.

## Коммерческий обзор и КП

### POLICY-3: политика обработки персональных данных

В каждом новом КП есть обязательный блок «Политика обработки персональных данных»:
сроки хранения, порядок удаления/уничтожения и условия передачи третьим лицам.
Он формируется общим генератором внутри разрешённого поля персонализации;
цены, другие разделы и файл утверждённого шаблона не меняются.

Для каждого пункта сохраняются status (PASS/REVIEW/FAIL), quote, source,
citations с координатами, объяснение и конкретный вопрос. В операторском запуске
это `policy3.json`, `assessment.json` и коммерческое обоснование. Пакетный маршрут
пишет `policy3.json`, старые экспорты сохраняют оценки в proposal-state/review JSON.

Автоматический поиск извлекает тематические цитаты только из доступных
воспроизведённых страниц/документов политики. Он не устанавливает полноту порядка
или правовую применимость: исходный статус — REVIEW. Отсутствие слова, частичный
пакет или недоступная политика никогда не превращаются в FAIL. Если цитата
не извлечена, quote=null с явным объяснением; при отсутствии источника source=null.
Старые bundles без Collector-пакета получают три REVIEW, а не выдуманные цитаты.

PASS и FAIL можно документировать в существующем локальном коммерческом обзоре:
необязательный массив `policy3` содержит элементы с `check=retention|deletion|transfers`,
`status`, `quote` (обычный TextGrounding), `explanation` и `confirmed=true`.
Для PASS/FAIL подтверждение обязательно. Проверяются хеш пакета, имя и время
проверяющего, отсутствие повторов, точная цитата именно из политики и её координаты.
В операторском маршруте обзор также привязан к analysis, как прежде.
Неверная цитата/привязка отклоняет обзор, а не создаёт обвинение.

PASS означает независимое подтверждение описания проверенного пункта в указанном
объёме, а не полное соответствие законодательству. FAIL — документированный
конкретный недостаток, например подтверждённое противоречие двух сроков для
одних и тех же данных. Смысл оценки подтверждает проверяющий; одна отметка
confirmed не заменяет содержательной проверки, имя не аутентифицируется программой.
Автоматического вывода о нарушении закона нет.

В клиентском КП при FAIL выводятся конкретный недостаток, цитата и источник;
при PASS/REVIEW — конкретный вопрос о сроках, действиях по удалению или получателях.
Технические коды остаются во внутренних результатах. POLICY-3 не повышает
самостоятельно юридическую доказанность и не снимает ручной запрет отправки.
Ручное заполнение всех трёх пунктов не требуется для Commercial MVP GO.

### Commercial MVP: одна находка и автоматическая подготовка КП

```bash
lexradar audit https://example.ru/ --dossier local-dossier \
  --saved-audit local-audit --output runs/commercial-mvp --commercial-mvp
```

`--commercial-mvp` разрешает коммерческий GO и автоматически создаёт
`proposal.html` без ручного коммерческого обзора, если есть хотя бы одна находка:

- `material=true`, статус potential/confirmed, фактическое утверждение present;
- полный `fact` совпадает с точной цитатой в объявленном воспроизведённом источнике
  (CONFIRMED); отсутствие данных в выборке или один совпавший фрагмент пересказа
  сами по себе не достаточны;
- наблюдение не классифицировано как positive_fact или no_issue;
- `proposed_work` содержит legal_documents и/или webmaster_instructions,
  а `additional_checks` описывает работы непустыми пунктами от 10 символов;
- аудит завершён успешно.

Доказанный состав нарушения, подтверждённая норма и `legal_position=possible_issue`
не требуются. Дословный факт и категории услуг берутся из существующего ответа
Single A. Конкретный результат формируется из выбранной услуги: письменное
заключение и проекты изменений документов либо протокол проверки и ТЗ вебмастеру
с критериями приёмки. Дополнительные проверки модели сохраняются как внутренние
предложения, а не утверждения для клиента. В клиентских карточках нет повторяющихся
оговорок и технических статусов; общие ограничения экспресс-аудита сохранены в шаблоне.
Перед клиентским выпуском проект нужно прочитать. При наличии локального
обзора его решение приоритетно: MVP не отменяет отрицательное решение проверяющего.

Для основной карточки приоритет у подтверждённого наблюдения об аналитике.
Cookie-уведомление с Метрикой и продолжением использования получает конкретный
текст о выборе пользователя, проверке загрузки аналитики, протоколе, ТЗ и документах.
Дополнительно включается только один короткий вопрос по специальным категориям
данных с реальными MATCH-наблюдениями, без длинной цитаты. Сам вопрос не даёт GO.
Для сохранённого аудита №101 это F003 и F004; F005/F007 остаются только внутри отчёта.
Неподтверждённый составной fact и обвинительные выводы модели не переносятся в КП.
Положительные, отклонённые и опровергнутые находки исключаются; отрицательный
ручной обзор также не обходится. Внутри одной темы сохраняется исходный порядок,
нового AI-ранжирования нет.

Получатель автоматически берётся из явного поля полного/сокращённого наименования
ООО в воспроизведённых источниках. При отсутствии однозначного подтверждения
используется «Руководителю клиники», без подстановки URL. Значение `--company`
также должно соответствовать подтверждённому наименованию. Выводимая версия
исправлена на v2.4; файл утверждённого шаблона, цены и остальные разделы не меняются.

В assessment сохраняются `commercial_mode=mvp`, `commercial_offer` с основанием,
индексами цитат, услугами и результатами. `proposal_findings` задаёт порядок
карточек, `supporting_findings` — дополнительные предположения, `proposal_role` —
primary/hypothesis. `operator_review` остаётся null, если человека не было;
юридические статусы не повышаются автоматически. Режим и выбранные карточки
также записаны в summary. Отдельно создаются `commercial-justification.json`
и `commercial-justification.md` — проект обоснования с фактами, возможными рисками,
услугами и результатами для клиента. Одной сильной находки достаточно;
утверждённый шаблон v2.4 и его условия сохраняются.

КП подготавливается локально. Во всех результатах `manual_approval_required=true`,
`manual_approval=null`, `automatic_send_allowed=false`, `client_release_allowed=false`,
`sent=false`. GO не является ручным утверждением. Команды отправки в этом маршруте
нет: клиентский выпуск и отправка остаются отдельным ручным действием после
утверждения проекта; `--send` не поддерживается.

Флаг можно добавить и к разрешённому платному запуску, но он не разрешает новый
AI-запрос сам по себе и не отключает скрининг, целостность, лимиты или подтверждение
передачи. Без `--commercial-mvp` сохраняется описанный ниже маршрут с ручным обзором.

Без документированного предмета услуги новый операторский маршрут возвращает
HOLD, сохраняя кандидатов и диагностику. Это дополнительный явный человеческий
этап, а не требование доказать нарушение для продажи обоснованной проверки.
Legacy интерфейсы остаются доступны с прежним консервативным отбором.

Чтобы разрешить коммерческий GO, заполните копию commercial-review-template.json
(в другом файле): имя, UTC reviewed_at, совпадающие packet_sha256/analysis_sha256
и массив findings. Пример одного элемента (не готовое согласование):

```json
{
  "finding_id": "ID из assessment.json",
  "quote_indices": [0],
  "factual_scope": "Какое конкретное наблюдение специалист проверил по указанной цитате",
  "risk_reason": "Какой конкретный вопрос требует проверки и почему услуга полезна клиенту",
  "deliverables": ["Документ по результатам проверки и конкретное ТЗ вебмастеру"],
  "services": ["legal_documents", "webmaster_instructions"],
  "factual_scope_verified": true,
  "service_need_verified": true,
  "positive_only": false,
  "legal_violation_verified": false,
  "verified_legal_sources": []
}
```

quote_indices — индексы с нуля; выбирать можно только MATCH. Нужны конкретные
фактический объём, риск/предмет проверки и результат работ. Шаблон с пустыми
findings никого не допускает в GO. Обзор проверяется на связь с байтами результата,
но сама запись имени не аутентифицирует оператора и не разрешает выпуск клиенту.

Применить обзор можно повторной бесплатной командой saved-audit с
--commercial-review /path/to/review.json и новым output. Хеши берутся из
шаблона, созданного именно для этой перепроверки; при изменениях они отклоняются.
При GO proposal.html персонализируется из побайтно закреплённого v2.4: только
четыре разрешённых поля, прежние дизайн и условия. Цитаты выбираются из MATCH,
объём работ — из локального обзора, а непроверенный риск явно отделён от нарушения.
При HOLD создаются report.md/report.html с причинами и следующими проверками.
Ни один маршрут не рассылает результаты и не устанавливает release_allowed=true.

Исходный текст модели, HTTP JSON envelope (новые live-запуски), structured JSON,
промпт и отправленный пакет сохраняются в audit/capture-A-1 и audit/analysis.json.
Известные секреты редактируются с отметкой capture.json; ключи/HTTP-заголовки
не сохраняются. При сетевой ошибке полного ответа может не существовать.
