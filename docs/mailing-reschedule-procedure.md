# Исполняемый инструмент переназначения, 09.11.2026

Текущая реализация — `mailing_reschedule.py`. Этот раздел заменяет ограничения
проекта ниже о нереализованном apply и расчёте после хвоста.
Новый расчёт: ближайший свободный слот позже now+10 минут, пн–сб
09:00–17:45 МСК, шаг 15 минут. Все старые слоты остаются зарезервированными;
до любого занятого времени выдерживается минимум 15 минут.

Из корня checkout, после загрузки ESPO_API_KEY штатным способом:

```bash
# Локальный предварительный расчёт, без сети:
python3 mailing_reschedule.py --limit 1000
# Полная безопасная API-сверка, только GET:
python3 mailing_reschedule.py --check-api --limit 1000 --output /tmp/lexradar-reschedule-api.json
# Отдельное применение после просмотра отчёта и исключения внешних писателей:
python3 mailing_reschedule.py --apply --limit 1000 --output /tmp/lexradar-reschedule-apply.json
```

По умолчанию лимит — один кандидат; непроверенные не считаются допущенными.
Apply повторяет свежий dry-run и требует охвата всей очереди; при изменении
Email между своим снимком и PUT останавливается. Блокировки mailing.lock,
.mailer.lock и shared CRM journal lock берутся без ожидания. Чужие API-писатели
этими блокировками не защищены. Нет POST/send/смены статуса или содержания.
Отдельный приватный журнал `.control-center-state/mailing-reschedule.json`
не удалять и не подменять: UNKNOWN требует ручной сверки и нового разрешения;
автоматического повтора или отката нет. Подтверждённые ID пропускаются.
Исходные копии с хешами сохраняются в state/reschedule-<operation ID>.

Ниже сохранена история исходного проекта; его таблица после хвоста устарела.

# Проект процедуры переназначения SCHEDULED, 09.11.2026

Подготовка, не разрешение на применение. По умолчанию dry-run: только GET и
отдельный приватный отчёт; никаких PUT, cycle(), send, POST, изменений очереди,
конфигурации или перезапуска. Реализация режима применения в эту задачу не входит.

1. Перед применением отдельно получить разрешение оператора. Исключить внешних
   писателей CRM и конкурирующее планирование. Взять mailing.lock, затем прежний
   .mailer.lock в порядке Mailing.cycle, без ожидания занятого lock. Сохранить
   приватные копии очереди и CRM-журнала с SHA-256, не заменять исходные файлы.
   Остановка панели сама по себе не останавливает отправку EspoCRM.
2. Отбирать только уникальные ключи SCHEDULED из mailing.json, сортировать по
   (старый slot, Email ID). Ключ должен совпадать с row.id. По source_id найти
   прежнюю :draft запись crm-prepare.json: steps.email.id, Account, Document,
   recipient и SHA-256 обязаны точно совпасть с очередью. Архив, старая партия,
   binding_hold, незавершённые/неизвестные операции и конфликтующие привязки — HOLD.
   schedule_intent, равный подтверждённому старому slot, сам по себе не ошибка;
   несовпавший или неподтверждённый intent блокирует перенос.
3. Первым сетевым действием по каждому кандидату читать полный GET Email/<id>.
   Допуск только при точном id, status=Draft, пустом dateSent и корректном sendAt
   строго в будущем, равном локальному slot. Проверить parentType=Account,
   parentId, единственного получателя, отправителя, отсутствие cc/bcc и прежние
   доказательства вложения Document/PDF/SHA-256. Недостаток доказательств — HOLD.
   Sent, неизвестный статус, отсутствующий/прошедший sendAt пропускать без записи.
   Ошибка/неполный GET останавливает весь проход, а не разрешает следующий PUT.
4. В dry-run сохранить исходный снимок/его хеш, время GET, причины исключений,
   старый и предлагаемый sendAt (UTC и МСК), число подтверждённых и непроверенных.
   Для небольшой проверки — один кандидат; лимит GET/времени задавать явно,
   без массового обхода Email. Непроверенные записи не считать подходящими.
5. Для применения необходим полный свежий список занятых sendAt через штатный
   API.scheduled с проверкой полноты; без него глобальная уникальность неизвестна,
   применение запрещено. Его массовое чтение сейчас не выполнять. Резервировать
   также все сохранённые intents. Минимальная безопасная стратегия — после хвоста
   всех существующих сроков, без уплотнения и освобождения старых слотов.
   Использовать next_slot: пн–сб 09:00–17:45 Europe/Moscow, 15 минут,
   строго позже now+10 минут и последнего занятого слота. В API — UTC
   YYYY-MM-DD HH:MM:SS. Один Email ID и один новый слот — один раз за операцию.
6. Применять последовательно. Непосредственно перед каждым PUT повторить полный
   GET Email и сравнить со снимком dry-run, повторно проверить Draft и будущее
   старое/новое время. Любое изменение — остановка и новый dry-run. До PUT сохранить
   отдельный durable intent (operation ID, Email ID, binding, старое/новое время,
   снимок/хеш, timestamp), атомарно с fsync, права 0600, каталог 0700.
   Единственная допустимая запись: PUT Email/<id> с одним полем sendAt.
   Не вызывать отправку и не менять статус, адреса, текст, вложения или сделки.
7. После PUT — полный GET. Успех только при том же id, Draft, точном новом sendAt
   и неизменных содержательных полях/привязках. Sent после PUT означает остановку
   и сверку, не повтор. Сохранить подтверждение, затем атомарно обновить только
   slot/schedule_intent/checked_at соответствующей строки очереди под lock;
   сохранить прежние значения в отдельном журнале операции.
8. Таймаут, обрыв, неожиданный ответ PUT/GET или сбой сохранения после намерения:
   STOP UNKNOWN для всей операции, сохранить intent, не повторять PUT и не
   откатывать автоматически. При рестарте сначала разбирать прежний журнал:
   подтверждённые ID пропускать; неизвестные блокируют продолжение. Отдельный GET
   может подтвердить новый срок, но старый срок сам по себе не разрешает повтор.
   Возобновление — только после ручной сверки и нового разрешения.
