# Ежедневный план 10 контрольных звонков — MVP

Дата реализации: 10.11.2026. Ветка: `web-control-development`.

## Реализовано

На существующей `/followup` добавлен раздел «План звонков на сегодня»:
московская дата, состояние, организации, телефоны, причина выбора, срок контроля,
ссылки на существующие Task и актуальные CRM status/callResult. Прежняя очередь,
фильтры, история и действия страницы сохранены.

Цикл: «Сформировать план» → предложение → «Утвердить план». Первое формирование
использует существующий отбор `daily_call_plan.plan`; повтор не пересчитывает
сохранённый снимок. Утверждение допускается для 10 организаций. Если пригодных
меньше 10, показаны причины, неподходящие задачи не добавляются. Неполный снимок
не пересчитывается автоматически; проверьте задачи и источники, следующий день
имеет отдельный план. Утверждённый состав сохраняется до конца московских суток.
Повторное утверждение не изменяет файл; устаревшие дата/отпечаток формы отклоняются.
Старые снимки CLI без состояния трактуются как предложения; недостающая привязка
восстанавливается при чтении по прежнему маркеру и штатным экспортным журналам,
без изменения состава и без записи результатов звонка в LexRadar.

Состояние: `.control-center-state/daily-call-plan-YYYY-MM-DD.json`, lock по дню,
права файлов 0600. Первое создание — прежний atomic hard link, дальнейшие изменения —
существующий `espo.save` (временный файл 0600, fsync, replace, fsync каталога).
Каталог уже исключён `.gitignore`. Повреждённый файл не очищается и не заменяется.

«Обновить статусы» перенаправляет на страницу, которая читает актуальные Task и
Account через GET. Просмотр не записывает CRM и не подбирает замену выбывшим.
Завершение, результат звонка, отказ, перенос срока или конфликт телефона остаются
видны в неизменном плане с пометкой «Не звонить» и без активной tel-ссылки.
При отказе чтения сохранённый телефон виден текстом; актуальность не заявляется.
Результат звонка оператор отмечает только в существующем Task.callResult EspoCRM.

Metadata читается до формирования, при просмотре сохранённого плана и повторно
перед передачей. Отсутствующий, readOnly, disabled или не date `callPlanDate`
отключает передачу; локальное предложение/утверждение и ссылки продолжают работать.
Недоступность Metadata не считается доказательством отсутствия поля.
Пользовательские поля через API не создаются.

Если поле доступно, только для утверждённого плана показана отдельная кнопка
«Передать план в CRM». Для каждой выбранной Task перед PUT заново читаются полная
Task и Account, проверяются ID/маркер/связь, срок, статус, callResult, телефон и
локальный запрет. Единственный payload: `{"callPlanDate":"YYYY-MM-DD"}`.
Чужая непустая дата не перезаписывается. До PUT атомарно сохраняется намерение;
после PUT выполняется GET, сверяются дата и остальные поля (кроме серверных
modifiedAt/modifiedBy). Потерянный ответ проверяется GET, слепой повтор PUT запрещён.
Результат отдельно показан у каждой строки; остальные Task не затрагиваются.
Ошибки показаны категорией/HTTP-кодом без приватного тела ответа.

Новые POST используют прежние Host/Origin/CSRF-проверки обработчика, проверяют
единственность полей, действие, дату и отпечаток состава. Новых подтверждающих
чекбоксов нет. Новые Task/Account/Email не создаются; сроки, ответственные,
описания, статусы и callResult не меняются. Рассылка, парсеры, шаблоны и права
EspoCRM не изменены.

## Изменённые файлы

- `daily_call_plan.py`: диагностика отбора, цикл состояния, Metadata, чтение
  актуальных статусов, явная передача даты, HTML раздела; CLI сохранён.
- `control_mvp.py`: подключение раздела и защищённого POST `/followup/plan`.
- `tests/test_daily_call_plan.py`: прежний тест сохранения и 9 коротких тестов MVP.
- Оба справочника CRM: дополнение о проверенном локальном поведении.
- Этот отчёт.

`control_followup.py`, `control_pages.py`, `src/lexradar/espo_export.py` изучены,
их функции и API-клиент переиспользованы без изменений.

## Ограничения живой проверки и действия оператора

Живой GET Metadata через существующий `espo.API` завершился
`CRM connection failed (PermissionError errno=1)`. Наличие поля, права записи и
реальные 85 Task этой средой не подтверждены. Публичные ссылки интерфейса ведут
на `https://crm.prostoburo.com`; существующий API-клиент и его внутренний адрес
не менялись. HTTP существующей страницы `127.0.0.1:8080/followup` недоступен
(код 000), процессы панели в доступном списке не обнаружены. Браузерная приёмка
не выполнена. Второй сервер не запускался, действующий сервис не перезапускался.
Живых PUT/POST CRM, писем, звонков, новых задач и изменений рабочих журналов нет.
Git add/commit/push не выполнялись; прежние чужие файлы сохранены.

Оператору:

1. После окончания активных заданий загрузить новый код одним штатным запуском
   текущего `control_mvp.py` по `docs/OPERATIONS.md`; исключить второй экземпляр.
   Учесть, что штатный запуск панели запускает уже существующий mailing worker.
2. Открыть `/followup`, сформировать предложение, проверить 10 организаций и
   причины, утвердить. Обновить статусы перед звонком, результат отметить в Task CRM.
3. Без поля даты пользоваться локальным утверждённым списком и ссылками.
   Если Metadata подтверждает поле и требуется метка в CRM — отдельно нажать
   «Передать план в CRM», затем проверить результат каждой строки.
4. При неизвестном PUT сверить `callPlanDate` в CRM вручную. Повтор кнопки читает
   подтверждённую дату, но не повторяет неподтверждённую запись; не удалять намерение
   ради обхода защиты. При повреждённом файле сохранить копию и разобрать причину.

Между GET и PUT остаётся окно внешней конкурентной правки: API не предоставляет
здесь серверный CAS. Состав фиксирован, актуальные статусы отражают момент GET;
карточку необходимо сверять перед фактическим звонком. Просмотр сохранённого плана
делает до 21 GET (Metadata и до двух на строку) и зависит от задержки CRM.
